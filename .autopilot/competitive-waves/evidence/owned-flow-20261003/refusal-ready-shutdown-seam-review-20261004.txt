1. Do not retain stale findings against current source
Initial candidate close_admission changed Preparing/Ready to Aborted. A caller that already received Ready could then commit, while worker exited and terminal join removed its registry entry; later publish blindly changed the detached slot to Committed and dropped the caller's last owner. This violated the accepted durable outbox/retained original guard contract.
Current source close_admission only sets registry.closed. It no longer mutates existing Ready/Preparing. Thus already admitted reservations remain valid responsibility: shutdown denies NEW registration, but terminal join waits for the admitted publisher to commit/resolve ambiguity or definitively abort. publish after close still wakes the live existing worker. This is the minimal correct separation of admission closure from cancellation of outstanding commit responsibility.
A second initial window was entry.handle=None between outer registration and actual thread-handle publication. Current join_slot waits REGISTRY_CHANGED while the entry exists without a handle, releasing the registry mutex. Spawn success installs the actual handle and notifies; definitive spawn failure removes the entry and notifies. Terminal join can no longer infer 'no worker' from an unpublished handle. Caller and original outer slot remain retained during that window. The actual handle is joined before registry removal. These are source-structural conclusions, not claims that the corresponding new tests compiled or passed.

2. Remaining bounded issue: reserve can join an unrelated indefinitely blocked shutdown before discovering closed admission
Source confirmed: reserve_inner invokes reap_finished before reading registry.closed or checking capacity. reap_finished enumerates completed entries and calls join_slot; join_slot enters the shared join_domain, whose Condvar waits while another join holds that domain.
Concrete interleaving:
- Entry A is a committed/pending delivery with unavailable journal/IO. Entry B has finished but is not yet reaped.
- close_admission sets closed. join_all begins join_slot(A), owns the join-domain token and legitimately waits indefinitely for A's actual worker.
- A new reserve calls reap_finished, sees B, and calls join_slot(B). It waits on the occupied join domain and never reaches the closed check returning Busy.
This breaks the closed-admission/nonblocking-capacity contract and can hold a synchronous reserve inside a runtime task during teardown. No SQL transaction is needed to reproduce it. A preliminary closed check alone narrows the window but does not close the race where shutdown closes/takes the join domain immediately after that check.

Minimal lifecycle correction
Keep close_admission's current deny-new-only semantics. Before constructing/installing a new slot, check closed under the short registry mutex and return Busy. Make reserve's completed-worker reclamation nonwaiting with respect to the global join domain: try-acquire its token, skip reclamation or return Busy when it is occupied, and recheck closed/capacity atomically under the registry mutex before registration. Reap only known completed handles; do not wait for unpublished/preparing/pending workers from the reservation path. Factor the reaper's use of an already acquired join token so it does not recursively call join_domain and deadlock itself. Actual joins remain outside registry/slot mutexes and outside SQL; registry outer ownership stays until join is real. It is acceptable to return Busy with finished entries pending reclamation while another terminal join owns the domain. Blocking join remains appropriate for definitive reservation rollback and terminal shutdown, not pre-admission resource housekeeping.
No change to claim tokens, immutable refusal receipts, current controls, journal authority, or physical cleanup is justified by this correction.

D. Remaining reap issue
Maintain A as a genuine pending delivery whose actual terminal join is blocked. Maintain a DIFFERENT finished/unreaped B. Close admission, start A's join, then call reserve for a different real original launch guard on another thread. Require prompt Busy WITHOUT restoring A's journal/disk, without new registry entry/thread/receipt, and without relying on a timeout to kill the reserve. Pair the close-between-fastcheck-and-reap race. Then restore A and let actual join complete. The fixture must contain B; a pending A alone makes reap_finished empty and would miss the defect.

Implementation constraints retained
