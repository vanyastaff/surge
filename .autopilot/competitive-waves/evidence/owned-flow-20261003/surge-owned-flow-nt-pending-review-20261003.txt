Exact draft reasoning

native_open always adds FILE_SYNCHRONOUS_IO_NONALERT. Directory access explicitly includes SYNCHRONIZE; lock and source access use FILE_GENERIC_READ/WRITE masks that include SYNCHRONIZE. There is no asynchronous option, no OBJ_INHERIT, and no added completion/oplock profile. Parent is borrowed, not transferred. The component buffer, UNICODE_STRING, OBJECT_ATTRIBUTES, HANDLE output and IO_STATUS_BLOCK storage are live and initialized throughout the SDK call. Immediately after return, STATUS_PENDING is tested before any output interpretation, OwnedHandle transfer, error return or IO_STATUS_BLOCK union read.

The branch calls std::process::abort directly. Rust documents that it never returns, terminates the entire process and runs no stack destructors, including those on other threads; it is not panic/unwind and invokes no panic hook. Consequently this branch does not return into a caller that can drop/reuse the pending output/vector storage, does not drop the parent owner as a normal refusal, and cannot continue to claim/provider effects. There is no guessed handle wait, unsafe ownership adoption, retry, background completion, or normal resource leak. Fatal process termination is the endpoint. This is a justified containment response to a broken external completion invariant, with process-wide availability cost, not a normal invalid-input/unsupported-platform response.
https://doc.rust-lang.org/std/process/fn.abort.html

Only completed STATUS_SUCCESS plus a valid handle reaches exactly-once OwnedHandle -> File transfer. Other documented final errors return without adopting the borrowed parent or arbitrary output bits. The Pending branch must remain before that handling. Replacing it with return Err, panic/unwind, treating positive Pending as success, or waiting on an unproved output handle would invalidate this focused acceptance. Supporting an actual asynchronous profile would require a separately designed completion/lifetime protocol and review; it is not authorized by this verdict.

Limits and follow-through

No claim is made that Rust storage remains independently useful after process termination or that this recovers from a compromised kernel. The argument is noncontinuation without normal teardown under a documented synchronous FFI contract. A caller-controlled bad pathname/reparse/access conflict must remain a documented final error, never intentionally mapped to the fatal branch. A conforming kernel/filter stack should not produce this status for the approved create profile.
