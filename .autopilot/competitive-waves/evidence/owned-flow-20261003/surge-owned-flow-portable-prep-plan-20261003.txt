2. Chosen private capability split
Keep one crate-private preparation facade, not a new crate or public generic filesystem API. Add private typed PreparationLockKey::Task(WorkItemId) / FlowOperation(WorkItemOperationId), and an internal requirement StableOwnership / RestrictedPrivateInputs. Capability is host-derived, never a JSON/config override. Task retains its current filename and Unix identity bytes; FlowOperation uses a distinct fixed prefix plus validated ID, never arbitrary caller path text. It cannot collide with Task locks.
Linux/macOS use the existing secure backend for both requirements, a superset of StableOwnership. Windows implements StableOwnership only. RestrictedPrivateInputs on Windows explicitly fails before private bytes/body capture or provider/MCP effects. A stable Windows lock is not an ACL/confidentiality proof. Unsupported filesystems also fail closed if real handle identity/locking is unavailable; do not silently use names, size/time, PID, timestamps or unsigned owner strings as substitutes.
The ordinary flow coordinator determines the effective frozen MCP input list once, including resolved defaults. Any transport inputs requiring the approved private-input store require RestrictedPrivateInputs; an empty/no-private-input route uses StableOwnership. Do not reclassify a populated default MCP server as harmless to make Windows pass. Provider inherited auth stays outside private capture; existing configured-source secure-platform refusal is unchanged. This amendment does not grant a new Windows configured-auth pin capability.

3. Windows backend, narrowly using standard-library ownership plus verified SDK metadata
Use std::os::windows::fs::OpenOptionsExt for access_mode/share_mode/custom_flags and std::fs::File for RAII and try_lock. This avoids introducing raw CreateFile handle transfer and a second locking implementation. Add only Windows GetFileInformationByHandleEx metadata queries through existing version-pinned SDK bindings.
For a fully qualified host-owned filesystem path, parse Windows root/prefix components explicitly (drive and UNC share roots; no device/named-pipe paths, alternate-stream components or drive-relative paths). Walk root to the lock parent component by component, retaining every File handle. Each directory open uses OPEN_EXISTING via std, FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT, FILE_READ_ATTRIBUTES, and a sharing policy without FILE_SHARE_DELETE. Use FILE_SHARE_READ only for held directories: do not allow other write opens to turn a held ancestor into a reparse routing boundary. This must be checked by the independent Windows API/unsafe reviewer, including ordinary child create/open operations under held parents and attribute/reparse mutations; attribute-access exceptions mean sharing flags alone are not a complete metadata invariant.
For each open, query FileAttributeTagInfo (reject all reparse points), FileStandardInfo (directory versus regular type, delete-pending, link count), and FileIdInfo (VolumeSerialNumber + 128-bit FileId). Require a regular, non-delete-pending, single-link lock file. Before each child/name use and finalization, freshly reopen/query each already held directory name and compare its actual IDs and required type/attributes with the held handles. The no-delete-share handles inhibit rename/deletion during ownership; actual fresh handle comparisons, including reparse attributes, remain mandatory. Do not infer identity from GetFinalPathName text or canonical path text.
Create the final lock file with create_new/read/write, OPEN_REPARSE_POINT, FILE_SHARE_READ | FILE_SHARE_WRITE and no FILE_SHARE_DELETE. Only raw ERROR_FILE_EXISTS from exclusive creation permits OPEN_EXISTING with identical no-follow/share flags. Other errors fail closed. Never OPEN_ALWAYS/CREATE_ALWAYS, truncate, unlink or replace an existing file. A concurrent creator is not an invalid-file retry loop. Acquire File::try_lock once on that exact File, map WouldBlock to Busy, then repeat the held/name checks. Do not clone/inherit/unlock the lock handle while the guard lives. Rust File owns closure exactly once.
Serialize a versioned private structural identity containing actual root-to-parent IDs plus lock volume/128-bit ID and namespace. Persist it write-once for the original operation snapshot. Every reclaim requires acquisition of the same named lock and exact persisted identity. New file/ancestor identity after death yields Attention/Conflict, never a newly inferred dead-owner proof. This retains abandoned/accepted operation tombstones and original allocated IDs. File ID reuse after deletion is not authorization to change an immutable operation snapshot; ordinary no-delete rule plus persisted full chain and no cleanup/adoption rules remain required. No hardlink/path replacement can grant concurrent ownership merely because a SQL lease token is old.

AMENDMENT — EMPTY MCP HOST AUTHORITY AND WINDOWS CHILD OPEN (supersedes the absolute-path child-open suggestion in section 3)

Owning pre-code verdict: ACCEPTABLE for the revised typed-empty + handle-relative design below; RESHAPE REQUIRED for the earlier absolute CreateFile child-open proposal. No code has been accepted or Windows behavior verified. These are two linked next-unit amendments, not changes to completed pre-dispatch.

A. Empty MCP requires no private-input HMAC key
Yes: the existing host-owned attempt/startup trust boundary can authorize a genuine empty effective list, without a key or private object. This is structural host provenance, NOT cryptographic authentication against a hostile writer of the registry/journal. Existing engine/work_items.rs pinned validates a nonserializable WorkItemLaunchClaim through SQL token/run/generation/active-item checks, loads the immutable accepted origin, hydrates its stored config, and derives the prompt. validate_resume additionally checks seq1 RunStarted, unique WorkItemAttemptBound context, actual workspace, frozen config, graph payload/hash, accepted origin artifact and exact prompt artifact relation. Public hashes are consistency checks; they are not a signature. Neither these checks nor a private HMAC protect against an attacker possessing unrestricted same-process/host-store authority. Do not describe a caller's plain hash/bool as this host boundary.

Store a discriminated frozen MCP snapshot in the immutable accepted attempt: Empty { selection: Explicit | HostDefault }, or Private { selection, exact public manifest, authenticated envelope/reference }. Empty is host-produced only after resolving the effective list ONCE and proving it contains zero servers; Explicit(empty) and HostDefault-resolved-empty stay distinct. No private object/key is loaded/created for Empty, including acceptance, first dispatch, cold resume or wake. DTO input choosing explicit empty is merely an input; it does not itself mint a capability.
At atomic acceptance bind Empty to the existing operation receipt/request identity, actual allocated item/run/workspace creation-owner, accepted FlowOrigin graph/raw-prompt relation and immutable attempt config. The flow-specific startup event repeats this exact typed snapshot and binding; RunStarted public MCP list must be empty. Prior to initial MCP resolution, host-only pinned hydration checks the real pending-owned-intent predicate (not validate_claim alone), exact accepted revision/binding/workspace and typed snapshot against the operation/attempt. Prior to cold resume/wake, validate_resume checks the actual startup journal's unique snapshot/binding, empty RunStarted public list and immutable accepted attempt together, plus the applicable durable continuation/control fence. Journal absence permits only a genuine pending first-start intent; it cannot supply resume authority. Existing Attention/Suspended claim validation alone is insufficient for effects.
Only that successful hydration constructs a private non-Serde ValidatedOwnedMcpSnapshot::Empty capability; fields/constructors are inaccessible to wire/config clients. It is tied to the exact run/binding/workspace/selection. Resolve/run code branches on this capability, yielding None/zero servers directly and skipping global registry fallback. Cold resume must bypass the public RunStarted mcp_servers overwrite for authenticated owned-flow snapshots. Missing/duplicate/mismatched startup snapshot, nonempty public MCP list, different accepted selection, changed run/workspace or wrong control refuses before MCP/provider effects. A transplanted Empty marker is rejected by binding checks even though it has no secret payload.
Private/nonempty snapshots retain the previous HMAC/private-object contract unchanged: whole-list order and manifests, exact command/args/env, purpose/schema/operation/request/run/item/workspace/server binding, existing-key-only hydration, no recapture/default fallback, explicit unsupported-platform refusal before sensitive capture/effects. Corrupt or missing private keys are never converted to Empty. An unknown older flow snapshot is not Empty; fail closed/recover explicitly. A populated HostDefault cannot become Empty merely because the current host defaults disappeared.
Required Windows outer oracle: Explicit(empty) and HostDefault-resolved-empty accept, dispatch and cold wake with zero MCP children/tools even after global MCP defaults become nonempty; no HMAC key/private directory access occurs (inaccessible fake private-key path should not impede Empty). Wrong binding/selection/startup manifest rejects with zero effects. A populated frozen list on unsupported secure platform rejects without persisting raw secrets or creating writers. Real host-owner intent and startup checks are the authority oracle, not a bare SHA assertion.

B. Held Windows handles + repeated absolute-path checks do NOT prove child-open no-follow
Microsoft explicitly exempts attribute/EA access from share restrictions. Excluding FILE_SHARE_DELETE proves a useful delete/rename exclusion, but does not establish that a held ancestor cannot be changed into a reparse boundary during a subsequent absolute-path open. Repeated checks only observe endpoints; a routing change and restoration between checks cannot be ruled out by them. Therefore the earlier OpenOptionsExt absolute component walk is not accepted as the complete algorithm. Do not implement it and claim safety from passing endpoint tests.
Use the documented user-mode NtCreateFile for every untrusted child open/create relative to the actual held parent handle: OBJECT_ATTRIBUTES.RootDirectory is that handle and ObjectName is ONE validated UTF-16 component (no separators, dot/dotdot, alternate stream colon, device path or embedded NUL). Set OBJ_DONT_REPARSE for name parsing, FILE_OPEN_REPARSE_POINT, explicit directory/regular type constraints and the appropriate synchronous I/O/access flags; reject every reparse result/attribute. The docs explicitly provide fail-on-reparse name parsing with OBJ_DONT_REPARSE. This places no-follow into the OS name-resolution operation; absolute path endpoint checks are not its substitute.
Bootstrap only the OS filesystem root (drive volume root or UNC share root) with a normal owned File handle, actual metadata/type/root identity checks and no-delete share; no untrusted descendant is opened by concatenated absolute path. Subsequent directory creation, directory name reopening, final lock FILE_CREATE and collision-only FILE_OPEN all use the held parent handle and one component. Keep the full parent/name/ID validation before/after locking/finalization to detect removed/replaced bindings; it supplements relative opens rather than authenticating a pathname string. Parent metadata mutation yields same held directory object or fail-on-reparse; it must never route resolution through a caller-controlled replacement ancestor.
Use existing windows 0.58 generated Wdk::Storage::FileSystem::NtCreateFile and Wdk::Foundation::OBJECT_ATTRIBUTES, not guessed extern signatures. Add only required workspace-managed features including Wdk_Foundation, Wdk_Storage_FileSystem, Win32_System_IO and Win32_System_Kernel (OBJ_DONT_REPARSE), as demonstrated by SDK cfg gates. Windows handle construction now has a narrow unsafe ownership boundary: validated successful status and initialized output only, immediately transferred once into OwnedHandle then File; every error closes any genuinely owned result, never closes borrowed parent handles, never reads uninitialized IO_STATUS_BLOCK. UNICODE_STRING byte lengths are checked for u16 bounds and buffer storage lives across the synchronous call; structs use SDK types/size_of, not manual byte layouts. No OBJ_INHERIT, no duplicate lock handle, no STATUS_PENDING/uncompleted operation treated as success. Independent unsafe/API reviewer must approve exact flags/status handling before author writes the backend.
Only STATUS_OBJECT_NAME_COLLISION from FILE_CREATE permits existing-name FILE_OPEN; sharing conflicts map to Busy where genuinely ownership contention, while reparse/access/type/identity errors fail closed. No FILE_OPEN_IF, truncate, path reopen fallback or retry-on-invalid. Direct File::try_lock continues to supply the OS exclusive nonblocking lease. Unchanged immutable structural identity and same-lock reclamation laws remain.
Primary evidence (user-mode API, not a guessed kernel-only primitive):

https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes

Assert either original-parent object identity or fail-closed, never a lock under the substitute tree. Test final-component reparse creation/open, owner death, path/ancestor replacement, ordinary child creation while ancestors are held, Unicode/long/UNC paths, exactly-one cross-process holder and no secret capture. AMENDMENT — OF-P25-CRITIC-01: STABLE OWNED-FLOW CLAIM THROUGH EFFECT LIFETIME

Owning verdict: ACCEPTABLE for this bounded resolution; the prior preparation-only ownership plan was incomplete. Actual owned-flow effect ownership must not fall back to the legacy Windows claim verifier. No platform code is authorized before independent review of this amendment and the pending SDK/unsafe shape. This is new-unit pre-code reshaping, not another repair of the prior completed unit.

Use a distinct private PreparationLockKey::FlowLaunch { operation, run } namespace, rendered from validated host-allocated IDs. This is neither a Task key nor the FlowOperation preparation key. The existing/new StableOwnership OS primitive supplies this lease on Unix and Windows; it remains an OS exclusion/identity capability, not pending-intent/provider permission.
During the original request-scoped preparation, acquire the FlowLaunch guard outside SQL while holding the FlowOperation guard, using a fixed lock order Operation -> Launch. Persist its exact structural identity, key/namespace version, original operation and allocated run write-once in the provisional snapshot BEFORE acceptance. Keep both guards owned by the same preparation worker through freeze/finalization. Retry after genuine owner death acquires the same locks and compares both saved identities; if the launch object/ancestry has changed, refuse without replacing IDs or resetting the snapshot. A failure before this new launch-identity snapshot exists may finish its first capture under the unchanged original allocated IDs; no accepted attempt or provider owner exists yet. Already saved identity is never overwritten.
The atomic accepted item/revision/attempt/owned-intent/operation-receipt transaction includes this exact launch-lock binding and structural identity. Guard release after acceptance does not remove/unlink either stable lock or discard the identity. It does not set Prepared, launch a provider, or leave a claim token behind merely because preparation acquired a launch lease. This avoids a post-acceptance first-identity bootstrap where a substituted pathname could become the new original.

Keep WorkItemLaunchClaim as the genuine host-only engine boundary. Replace its private lock storage with a private enum Legacy { Arc<File>, path } / OwnedFlow { Arc<StableOwnershipGuard>, operation, run, persisted_identity }, preserving Clone by sharing the same OS guard through Arc rather than reacquiring/cloning an OS handle. No public/Serde constructor, no public optional boolean for choosing the weaker mode. Do not store the SQL-abandoning StartPreparation guard in the claim; reuse only its lower OS primitive. The last Arc drop releases the actual lease after daemon supervisor and Engine effect task both finish. WorkItemStore::claim(run) must inspect authoritative accepted origin/owned intent before selecting its lock implementation. Owned-flow origin routes exclusively to a private claim_owned_flow path; missing/malformed owned intent/launch binding is refusal, never a legacy fallback. This ensures existing daemon launch_attempt and cold reconciliation callers cannot accidentally take the weak branch. Other legacy task records retain their existing API/backend unchanged. A wire request cannot opt into Legacy for an owned flow.
claim_owned_flow loads expected original operation/run/namespace/structural identity, acquires the exact FlowLaunch OS guard OUTSIDE the registry write transaction, and verifies actual held/name identities against that persisted binding. In a short IMMEDIATE transaction recheck the immutable accepted origin/revision/workspace, exact owned intent and current generation/control predicate, active run and unarchived item, then recheck held OS identity BEFORE updating claim_token. validate_claim matches its private lock variant against the attempt's typed origin. Revalidate the claim at every existing effect-authority boundary; ownership is retained across admitted open/prompt through the same Arc, including after intent Started acknowledgment.
