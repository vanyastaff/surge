Actual problem confirmed

ObservedTransport::cleanup_task extracts child and schedules a Tokio task; Drop calls it, and rmcp ChildWithCleanup also starts a Tokio task on Drop. Outside an entered runtime this can panic; runtime shutdown can cancel detached cleanup before actual exit while dropping the observer/claim. Current daemon drain does not count that cleanup task. Transport close/JoinHandle success alone is not host writer disappearance proof.

Verified actual child primitive

Pinned process-wrap ChildWrapper defaults delegate start_kill/try_wait to the raw Tokio child. CommandWrap with no registered wrappers returns that raw child; tokio_cmd.process_group(0) configures its Unix PGID but does not install a ProcessGroupChild or JobObjectChild. Tokio1.50.0 Child::try_wait calls its platform child's synchronous try_wait, and on Ok(Some(status)) transitions to FusedChild::Done and disables kill_on_drop. Its Unix implementation delegates to std Child::try_wait/kill; Windows delegates to std handle-backed child. Neither synchronous method polls async process IO or needs an entered Tokio runtime. This source shape is credible for outside-runtime polling; native runtime oracles remain required.

Only the actual owned plain child is eligible for this algorithm. Do not flatten wrapped children through process-wrap unsafe inner methods, use ProcessGroupChild waitpid caches, or signal a remembered PID/group after uncertain reaping. At-most-once start_kill before any exit/wait-error plus permanently Ambiguous handling avoids repeated numeric kill attempts. A genuine child held by this parent cannot be replaced by merely editing an unrelated PID field. This assumes no separate parent thread manually reaps the same child; the private owner has exclusive wait authority.

Ownership / failure / ACK / tracker analysis

Pre-reserving bounded global capacity and successfully starting the OS worker before physical spawn prevents resource/thread-creation failure from leaving an untracked live process. Clone exact observer/claim before spawn. Register reservation before the first post-spawn await. Transfer the actual child and observer synchronously to the already running thread; failed channel send must return its parcel into the same synchronous settlement algorithm without dropping ownership. Missing stdio uses that path too. NoChild is only a spawn-error/no-process outcome, never a close ACK or inferred disappearance.

The implementation must retain the reservation until Start or genuine NoChild even when terminal Immediate arrives before parcel transfer; a shutdown request does not mean there is no child. This follows the draft's explicit Start/NoChild ownership contract. The tracker must preserve outstanding reservations, active workers and completed join handles until terminal joining or bounded reclamation; do not lose handles merely because an exit registration is removed. Never hold the tracker mutex while joining a worker which needs it to record completion. Concurrent barriers serialize and permanent terminal admission closure prevents a new reservation appearing behind a successful barrier. No live owner eviction or timeout-to-success is allowed.

ObservedTransport holds pipes plus a control/completion ticket, not process ownership. Its close starts Graceful synchronously before returning the future; Drop upgrades to Immediate. A never-polled/cancelled close cannot cancel the settlement worker. Async ACK is valid only if backed by actual Ok(Some(status)); sender disappearance, thread join error or ticket/channel closure is not successful exit. Standard thread owns child/claim independently of runtime destruction and transport caches. Active polling also detects natural exit. Grace expires into one kill, then actual try_wait; errors are opaque unknown and can honestly block terminal joining indefinitely. Do not release observer/claim on a timeout, unsuccessful kill, ambiguous wait or thread failure.

Leader versus descendant boundary

This amendment only settles the actual plain child leader. Killing/reaping it does not establish process-group or descendant disappearance despite process_group(0). The required descendant-survivor cold restart oracle is material, not optional. No new group/job wrapper is authorized here; that would require separately reviewing reaping state and ID reuse. Terminal barrier success likewise means these actual tracked children exited and threads joined, not all descendant effects globally contained.

Latest host exit paths: resolved at design level

Initial draft missed CLI process::exit(130), failed ping and the deliberately exceptional helper exit. Current plan replaces these with private numeric ExitRequested outcomes and performs the terminal barrier before returning the original status. Normal CLI uses runtime Drop; InternalStageMcp is parsed before runtime creation and uses shutdown_background before the independent barrier to avoid the known uncancellable Tokio stdin blocking read. The helper is a stdio/socket proxy, not a local MCP child registry; the explicit remaining-worker barrier is still required. Mode-specific unwind ordering is retained. UI window-creation failure becomes recorded status/cx.quit rather than process exit; daemon pre-engine profile load failure returns to normal terminal PID-lock cleanup. Runtime enter guard must drop before runtime. PID lock remains held until child workers settle. Actual host/helper smoke with stdin kept open is needed, not mechanical runtime Drop everywhere.

Tokio documents that runtime Drop waits for blocking work indefinitely and shutdown_background can leave such work running; these leaked stdin tasks are NOT child settlement proof. The terminal barrier is independent of them and permanently closes worker admission. Source: https://docs.rs/tokio/1.50.0/tokio/runtime/struct.Runtime.html#method.shutdown_background .

Bounded unresolved finding MCP-SETTLE-PANIC-01

The draft says catch_unwind around each operation produces only a fixed fatal containment category and no raw diagnostic prose. catch_unwind does not control panic-hook emission. Rust invokes the hook before the panic is caught; current CLI install_panic_hook delegates to the default hook, which can display an arbitrary payload/backtrace. Merely replacing the eventual catch result with a fixed code does not establish opaque diagnostics. The same applies to the synchronous post-spawn transfer/missing-stdio fallback if it uses the worker panic policy.

Required clarification: define an effective settlement-operation panic-hook boundary (including fallback) that emits only safe fixed metadata before abort, without process-global hook swapping races; or explicitly narrow the guarantee and prove that the closed plain-child operation profile cannot produce secret-bearing panic diagnostics. Do not assert catch_unwind sanitizes hooks. A thread-local suppression flag respected by the installed production hooks, with safe handling of test/downstream hooks, is one possible shape; a dedicated process-wide opaque panic policy is another. Raw panic payload must not be Debug/Display logged or dropped before abort (payload destructor can itself panic). Keep ChildParcel outside the closure and abort with child/observer still owned; no panic creates an exit/suspension/continuation receipt.
Primary Rust contract: https://doc.rust-lang.org/std/panic/fn.catch_unwind.html . This is a bounded opacity question, not a request for general application panic redesign or optional graceful recovery from a corrupted child wrapper.
