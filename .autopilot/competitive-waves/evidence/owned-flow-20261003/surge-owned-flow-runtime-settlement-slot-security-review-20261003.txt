Ownership and unwind

Caller holds an outer Arc<Mutex<Option<ChildParcel>>> from successful standard spawn through handoff. The actual child and exact observer are deposited before fallible pipe registration, and pipe extraction borrows rather than removes them. Start carries only an Arc clone. If send unwinds and destroys the message clone, the retained outer Arc still owns the slot; if the worker already took the parcel, its outer local owns it. Neither case leaves the sole child/claim inside an unwinding channel message. Poison causes immediate abort with the outer Arc alive, without unsafe recovery, error formatting or unwrap panic.

Worker takes Option once and installs it into its retained outer local before any caught operation or Taken send. The final code must keep that move free of callbacks or injected panics between Option::take and outer-local establishment; the design's private closed profile permits that direct non-fallible ownership move. Physical-spawn-to-slot initialization similarly preserves the actual child in an outer local until deposit. No custom spawn/pre_exec/allocator callback is admitted. OOM abort is not synthetic settlement.

Taken is ownership handoff only, not child exit. Caller retains the slot until synchronous Taken receipt. The channel carries no sole lease-bearing parcel. Send failure or lost Taken checks the slot under the same mutex: Some grants exclusive fallback ownership; None means worker ownership and requires Immediate plus actual worker completion. It cannot fabricate NoChild or return a live sole-owner StartFailed. A completed worker before Taken is acceptable only through observed exit plus joined handle. Failure paths preserve the registered reservation and OS thread handle. Standard child, observer, and completion destruction order remains unchanged: actual exit, child Drop, observer Drop, then publication/removal; fallback reports explicit Settled after the same order.

The implementation must not hold the slot mutex while child settlement, observer destruction, tracker joining, or waiting for Taken/completion. Only the ownership take/borrow needs the slot lock. This follows the defined take-then-outer-local protocol and existing no-lock-across-join constraints; it is an audit obligation rather than a new plan amendment.

Panic opacity remains valid

Section 6c still applies to transfer dispatch, borrowed pipe operations, poison/fallback and worker operations. The once-installed host dispatcher consults private TLS and emits nothing in protected scopes. Catch aborts immediately without dropping/formatting payload or retained parcel/slot, and does not restore TLS on unwind. The new slot does not require per-operation global hook changes or a public caller authority flag. Deliberate send-panic injection occurs with the already retained slot and therefore tests the actual gap. Worker and fallback fatal subprocesses must still install a payload-printing prior hook and demonstrate sentinel absence in actual stderr/TRACE. Rust's catch_unwind contract remains the primary reason hooks and payload destruction need separate handling: https://doc.rust-lang.org/std/panic/fn.catch_unwind.html .

Shutdown and cold semantics remain bounded

Sticky pre-Start Immediate and permanent admission closure still include all pending transfer/fallback reservations in the barrier. A new slot or Taken message does not unregister a reservation, free capacity early, remove a join handle or acknowledge exit. Synchronous handoff before the first post-spawn await prevents cancellation from abandoning a slot; worker control remains runtime independent. Tracker handles must also remain visible across concurrent finished-handle reaping/serialized terminal joining. Fresh terminal test scenarios isolate subprocesses; production admission never reopens.

Nothing in this amendment broadens direct-child settlement into descendant containment or suspension/continuation authority.
