2. macOS opaque ACL FFI soundness
Reviewed both ACL wrappers (secure_lock.rs:91-154; configured_route_pin.rs:200-260). Installed Apple SDK sys/acl.h confirms pointer-shaped acl_t/acl_entry_t, integer enum tag/type ABI, function signatures, FIRST=0, NEXT=-1, EXTENDED_DENY=2 and TYPE_EXTENDED=0x100. Its comment explicitly describes 169 entries fitting the extended binary representation. The bounded 170 iterations allow all 169 entries and a terminator, and fail closed for an unexpected longer result.
acl_get_fd_np receives a live borrowed File descriptor. A nonnull allocated ACL gets one RAII owner and one acl_free; entries are borrowed only while that ACL remains live. Writable outputs are correctly typed pointer/int storage; no Rust reference is formed to opaque C memory. All calls complete before ACL destruction. Only deny entries pass; grant/unknown/null outputs and non-end errors reject. FIRST precedes NEXT. Apple documents success as zero and exhaustion of NEXT as EINVAL, consistent with the implementation; absent-ACL ENOENT is accepted only on a live descriptor after file/directory safety inspection. I found no UB, double-free, dangling entry, invalid enum construction or descriptor leak in these wrappers.
