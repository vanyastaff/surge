# Интерфейсы

Читается каждым исполнителем **до** первой строки кода.

## Правила проекта, которые нельзя вывести из тикета

- **Стек:** Rust 2024 edition, MSRV 1.96, `tokio`, `rusqlite` + `r2d2`,
  `agent-client-protocol` 0.10.2. Воркспейс — 12 крейтов под `crates/`.
- **Сборка:** `cargo check` → `cargo clippy --workspace --all-targets --all-features -- -D warnings` → `cargo nextest run` → `cargo fmt`.
  Зелёными должны быть все четыре. `cargo nextest` предпочтителен `cargo test`.
- **Ошибки:** `thiserror` в библиотечных крейтах, `anyhow` в CLI.
- **Запрещено:** `unwrap()` в библиотечном коде — только `?` или явная обработка.
- **`#[must_use]`** на функциях, возвращающих `Result`. Публичный API документирован `///`.
- **Тесты** живут рядом с кодом в `#[cfg(test)]`, интеграционные — в `tests/`.
- **ID** — ULID через крейт `ulid`. **Хеши** — переиспользуй `surge_core::content_hash`, не заводи второй механизм.
- **Никаких новых внешних зависимостей** без явной необходимости (R46). Ни одной зависимости
  от пакетов DeepSeek Harness, Cordis или любого проекта из разбора (R43, R46).
- **Отсутствующая зависимость или недоступный инструмент — это `BLOCKED` в отчёте, а не установка.**
- **Не трогать:** `.autopilot/`, `docs/competitive-plan-2026-09.md`, чужие незакоммиченные файлы
  (`crates/surge-ui/src/components.rs`, `crates/surge-ui/src/screens/inbox.rs`, `findings.json`).
- **Версионирование схем:** новый event-пейлоад или ключ `surge.toml` → бамп по `docs/schema-versioning.md` (R53i).
- **ADR:** несущее решение → файл в `docs/adr/` по форме существующих (R52i).
- **Исполнение (R42):** работа ведётся агентами Rust Code Studio — `rust-scout` для локации,
  `rust-builder` для реализации, `test-engineer` для тестов, `rust-reviewer` для ревью.

## Поправка №2 к контракту таска 05 — **несущая для тасков 06, 07, 08**

Поля `MemoryClaim` **приватны**. Читать только через геттеры:
`claim.id() -> MemoryClaimId`, `.text() -> &str`, `.provenance() -> &Provenance`,
`.confidence() -> Confidence`, `.status() -> ClaimStatus`.

Конструирование — только `MemoryClaim::new(...) -> Result<Self, UnprovenVerifiedStatus>`
либо `MemoryClaim::from_transcript(text, source, hash) -> Self` (инфаллибельная).

`Deserialize` написан **руками** и проходит через тот же валидирующий путь: JSON со
`status: "verified"` без `verified_by`/`verified_at` отвергается. Причина, по которой
`derive` не годился: он разворачивается внутри модуля-владельца и видит приватные поля,
то есть приватность одна инвариант не держит.

Поля `Provenance` (`source`, `hash`, `verified_by`, `verified_at`) остались публичными.

## Контракт локаторов памяти — **обязателен для таска 07**

Аудит (таск 08) разбирает `Provenance.source` по форме и **молча пропускает всё,
что в неё не попало**. Ревью нашло, что сегодня аудит на реальной машине разобрал бы
ноль записей и остался зелёным: единственное, что наполняет `memory_claims`, —
backfill из v1 с источниками `legacy:<table>:<id>`, исключёнными из обеих проверок.

Чтобы этого не повторилось, форма локатора фиксируется здесь как контракт, а не как
соглашение внутри одного модуля:

| Вид записи | `Provenance.source` | Что с ней делает аудит |
|---|---|---|
| Утверждение о файле репозитория | путь к файлу относительно корня проекта | сверяет `Provenance.hash` с текущим `ContentHash::compute` содержимого; исчезнувший файл → `SourceMissing` |
| Утверждение, извлечённое из хода рана | `transcript:run-<ULID>#turn-N` | коррелирует с исходом рана `<ULID>` |
| Мигрированная запись из v1 | `legacy:<table>:<id>` | не проверяется ни на устаревание, ни на корреляцию — источника уже нет |

**Таск 07 обязан писать одну из первых двух форм.** Собственная форма локатора —
это молчаливое отключение аудита для всех записей, которые он произведёт: аудит не
упадёт и не пожалуется, он просто ничего не найдёт.

## Предупреждение для таска 03 — форма `SkillRef.hash`

Резолв скилла считает идентичностью **хеш** (§4 спецификации): кандидаты с одинаковым
хешем — это один пак, найденный по двум путям, и любой из них корректный ответ;
`SkillError::Ambiguous` остаётся только для кандидатов с **различающимся** содержимым.

**Форма поля (закрыто):** `hash: Option<ContentHash>`. `None` означает «матчить по
имени, провайдеру и версии» — ровно то, что порождает объявление `skills = [...]` на ноде
флоу. Каждый `SkillRef`, вернувшийся из `discover()`, несёт `Some`: обнаружение всегда
знает настоящий хеш. Сентинела `ContentHash::compute(b"")` больше нет — он был скрытым
протоколом в комментарии и неотличим от честного хеша пустого пака.

**Обход** защищён множеством с ключом `(SkillProvider, PathBuf)`, а не одним каноническим
путём: один физический каталог, объявленный и как `ProjectDir`, и как `UserDir`, даёт паки
под обоими провайдерами. Ключ только по пути схлопывал второй корень молча.

> ✅ **ЗАКРЫТО.** `resolve` возвращает **пару** `(SkillRef, ResolvedSkill)`: свежая
> идентичность приходит от библиотеки, а не восстанавливается вызывающим через
> обратный поиск по хешу. Гонка между `discover()` и `resolve()` стала невозможной,
> а не маловероятной. Обратный поиск из CLI удалён. Есть тест, который меняет пак
> на диске **между** обнаружением и резолвом и требует новую версию.
>
> **Никогда не восстанавливай идентичность резолвнутого пака перекрёстной ссылкой
> в каталог** — она устареет ровно в тот момент, когда это важно.
>
> <details><summary>История находки</summary>
>
> **Открытая правка в этой зоне (найдено при ревью таска 04).**
> `SkillCatalog::resolve` уже вычисляет свежий `SkillRef` и **выбрасывает его**:
> `let (_fresh_ref, resolved) = scan::load_skill_pack(...)`. Из-за этого каждый
> вызывающий вынужден восстанавливать идентичность поиском по хешу — и ловит гонку
> между `discover()` и `resolve()`: если пак изменился между ними, ни одна запись не
> совпадёт, и наружу уходит `None` без объяснения. CLI таска 04 уже на это наступил.
>
> **Условие: `resolve` возвращает пару `(SkillRef, ResolvedSkill)`.** Это убирает целый
> класс, а не один симптом. Любой таск, которому нужна идентичность резолвнутого пака,
> должен получать её от библиотеки, а не восстанавливать поиском.
> </details>

## Дисциплина сборки — обязательна для всех исполнителей (добавлено 2026-09-06)

Оболочка в этом окружении **падает от тяжёлых сборок**. Симптом: команды начинают
возвращать код 1 без вывода или SIGABRT (134), и обратно само не чинится — только
перезапуском. Воспроизведено на свежей загрузке, без параллельных агентов, при
`cargo -j 8`: хватило трёх сборок подряд.

Замер, объясняющий причину: `ulimit -u` = 252052 (не связывает), `/proc/loadavg`
показывает свободную систему, но `ps -eLf | wc -l` изнутри сессии даёт **31 задачу** —
то есть оболочка живёт в песочнице со своими, куда более тесными лимитами.
`cargo` разворачивает десятки `rustc` и упирается в потолок песочницы, а не машины.

**Правила, обязательные к исполнению:**

1. **`cargo … -j 2`** во всех командах. Не 8, не по числу ядер.
2. **Мерить свой крейт, а не воркспейс.** `cargo clippy -p <твой крейт> --all-targets
   --all-features -- -D warnings`, `cargo nextest run -p <твой крейт>`. Полный
   воркспейсный прогон — забота оркестратора, не твоя.
3. **Не запускать `cargo` без нужды.** Один прогон гейта в конце вместо десяти по ходу.
4. Если оболочка начала отвечать пустотой или кодом 134 — **остановись и верни
   `BLOCKED` с этим фактом**. Не пытайся «пробиться» повторами: не чинится, а
   состояние сессии портится дальше. Ложный зелёный из мёртвой оболочки хуже
   честного отказа — это уже проверено в этом прогоне.

## ⚠️ ПРИЧИНА ОТКАЗОВ ОБОЛОЧКИ УСТАНОВЛЕНА (2026-09-06) — не собирать в `/tmp`

Две мои предыдущие версии были **неверны**: ни число агентов, ни лимиты процессов
песочницы ни при чём. Настоящая причина в логе прямым текстом:

```
Disk quota exceeded (os error 122)
failed to write to `/tmp/claude-1000/verify-.../target/debug/deps/...`
```

**`/tmp` — это `tmpfs` на 31 ГБ, файловая система в оперативной памяти.**
Проверочные worktree создавались там, и каждая полная сборка воркспейса писала
несколько гигабайт в `target/`. Двух-трёх хватало, чтобы забить 31 ГБ — а вместе
с ними и память, отчего обёртка оболочки начинала падать с SIGABRT и отдавать
пустой вывод.

Сходится всё, чего прежние версии не объясняли: почему помогала перезагрузка
(tmpfs очищается), почему помогло ручное `rm -rf /tmp/claude-1000`, почему не
помог `sysctl kernel.pid_max`, и почему отказ наступал ровно после третьей сборки.

**Правило:**

1. **Никогда не собирать в `/tmp`.** Проверочные worktree — только на диске,
   например `/mnt/data/dev/.surge-verify`.
2. Если worktree всё же в `/tmp` — обязателен `--target-dir` на настоящий диск.
3. После проверки worktree **удалять**: `git worktree remove` или `rm -rf` + `git worktree prune`.
4. `df -h /tmp` перед тяжёлой сборкой стоит дешевле, чем полдня диагностики.

Правило `-j 2` из раздела выше остаётся в силе, но по другой причине: оно
экономит память, а не обходит несуществующий лимит процессов.

## Правило, добавленное после третьего повторения (2026-09-06): доказывай достижимость

Четырежды за прогон исполнитель построил механизм правильно и **не свёл его с боевым
входом**, и все четыре раза тесты были зелёными:

| Таск | Что построено | Почему не работало |
|---|---|---|
| 03, круг 1 | резолв скилла, хеш, событие, approval | инструкции выбрасывались; запрос летел событием, которого не рендерит ни одна поверхность |
| 03, круг 2 | approval на неоднозначность | резолв стоял **до** гейта, и половина реального корпуса умирала, не дойдя до человека |
| 13 | guard'ы цикла и spill | диспетчер создаётся только при наличии MCP-реестра, а боевой путь CLI передаёт `None`; пороги конфига не читает никто; потолок по времени опрашивается только при вызове тула |
| 11 | признак ёмкости в inbox | `classify` короткозамыкает на `is_terminal()`, а ран, упавший по 429, **терминален**: сканируется класс, где сигнала нет, пропускается тот, где он есть |

Общее у всех четырёх: **юнит-тест проверяет компонент, а не то, что до компонента
доходит управление.** Компонент безупречен, путь к нему отсутствует, счётчик
зелёных растёт.

Четвёртый случай — другой подвид, и он опаснее, потому что грепом не ловится. В
тасках 03 и 13 вызывающего **не было**; в таске 11 вызывающий есть, тест на боевом
пути есть, но фильтр отбирает **не тот класс входов**. Оба вопроса ниже отвечались бы
«да», и признак всё равно не появился бы ни на одном настоящем ране. Отсюда третий
вопрос.

> **Условие для каждого таска, добавляющего поведение:** приёмка обязана содержать
> хотя бы один тест, который идёт **боевым путём** — через `Engine::start_run`,
> через CLI-команду, через существующий движковый харнесс, — а не зовёт новый код
> напрямую. И прежде чем отчитаться, ответь себе на два вопроса:
>
> 1. **Кто вызывает мой код в проде?** Найди вызывающего грепом, а не предположи.
>    Если единственные вызывающие — в `mod tests`, фича не существует.
> 2. **Кто на другом конце?** Если код что-то отправляет — событие, запрос,
>    артефакт, — найди того, кто это принимает и отображает. Отправитель без
>    получателя это журнал, а не функция.
> 3. **На каком настоящем входе это сработает?** Не «сработает ли на моём фикстуре»,
>    а какой класс реальных данных сюда доходит — и не отсекает ли его условие
>    выше по течению. Если фича читает признак из упавших ранов, а фильтр берёт
>    живые, оба предыдущих вопроса ответят «да», и признак не появится никогда.
>
> Ответ «оно вызывается из места, которое я не проверял» — это `BLOCKED`, а не `DONE`.

## Факт о `RunStatus`, который обязан знать каждый, кто фильтрует раны (2026-09-06)

Найдено на втором круге ревью таска 11. Касается **не только его** — таск 09 (Run Report)
и таск 12 (парковка) читают те же сводки.

**`RunStatus::Crashed` не является исходом пайплайна.** Его назначает сам
`Storage::list_runs`, переписывая `Running`/`Bootstrapping` → `Crashed` при мёртвом pid
демона (`crates/surge-persistence/src/runs/storage.rs:324-336`) — **внутри того самого
вызова**, которым потребитель получает список.

Следствие, о которое уже споткнулись: любой фильтр вида `status == Failed` **молча теряет
раны, умершие в рейт-лимите**. Ран, упавший по 429 и переживший смерть демона, несёт
`StageFailed{429}` в журнале, но в сводке читается как `Crashed`.

То же верно для `Aborted`. Безопасен только `Completed` — у завершённого рана есть
`StageCompleted`.

> **Правило:** фильтруя раны по статусу, перечисли **все** варианты `RunStatus` и напиши
> по каждому, почему он включён или исключён. «Остальные по построению сигнала не несут» —
> не обоснование, а предположение; в этом конкретном случае оно оказалось ложным.

Это **пятый** случай дефекта достижимости за прогон и второй подряд подвида «фильтр выше
по течению отрезает реальный класс входов» — см. вопрос 3 в правиле выше.

## Долг производительности, принятый к исправлению в таске 11 (2026-09-06)

`surge inbox` начал читать журнал целиком у каждого упавшего рана **на каждом вызове**, а
у нетерминальных — дважды (`fold_run_state` и скан ёмкости отдельными проходами), причём
`classify` выполняется до применения `limit`. Условие: скан ёмкости складывается в
существующий проход `fold_run_state`, сканируются только раны, пережившие усечение.

Общий принцип для остальных тасков: **новый признак не заводит второй проход по журналу.**
Если признаку нужны события, он едет в уже существующем проходе.

## Урок круга 3 таска 11: две починки могут погасить друг друга (2026-09-06)

Найдено финальной проверкой. Форма дефекта неочевидная — по отдельности обе правки верны,
дефект возникает **только на их стыке**, и ни один тест каждой из них его не видит.

**Что произошло.** Ревью потребовало двух вещей одновременно:
- разделить узкий классификатор (маршрутизация) и широкий (наблюдение ёмкости);
- сделать так, чтобы состояние «исчерпан» истлевало при восстановлении.

Исполнитель сделал обе. После разделения `record_failure` заводит окно ёмкости по
**широкому** набору, а флаг `rate_limited` ставит по **узкому**. А ветка очистки была
завязана на `rate_limited`. Итог: для четырёх образцов, которые есть только в широком
наборе, состояние «исчерпан» стало **неснимаемым** — ровно тот вечный `Known(EXHAUSTED)`,
который вторая правка объявила починенной.

Тест второй правки строил нужное состояние и **останавливался за строку** до вызова,
который бы его обнажил.

> **Правило:** если в одной функции два предиката разной ширины, то состояние, снимаемое
> под guard'ом по **узкому** предикату, недостижимо для всего, что попало туда по
> **широкому**. Жизненный цикл состояния гейти **наличием самого состояния**, а не
> соседним флагом, который «обычно стоит вместе с ним».

**Как ловить.** Когда закрываешь два условия одного ревью, спроси: *не создаёт ли первая
правка вход, которого вторая не видит?* Тесты этого не покажут — каждый проверяет свою
правку на своём входе. Нужен один тест, идущий **через обе**.

Побочный урок оттуда же: расширение счётчика-основания (`total_failures` →
`observed_failures`) было **строгим надмножеством**, поэтому шум оно не уменьшило, а
увеличило. Расширяя источник сигнала, проверяй, что решаешь задачу «стало видно больше
нужного», а не «стало видно больше всего».

## Ловушка `TMPDIR`, которую порождает наша же дисциплина сборки (2026-09-06)

Мы запретили работать в `/tmp` (tmpfs 31 ГБ в оперативке — полная сборка его исчерпывает
и роняет оболочку). Правильный ответ на это — вынести `TMPDIR` на `/mnt/data`. Но **не
внутрь репозитория**.

Ревьюер поставил `TMPDIR=target/review-tmp` и получил падение
`surge-acp registry::tests::test_load_from_toml` (`left: 3, right: 0`) — и сперва
записал это как дефект диффа. Проверил, отозвал, назвал причину точно:

тест делает `set_current_dir(std::env::temp_dir())`, а `Registry::load_from_toml` →
`SurgeConfig::discover()` **идёт вверх по дереву** и находит собственный `surge.toml`
репозитория, в котором ровно три агента (`claude-acp`, `myagent`, `test-agent`).
С `TMPDIR` вне репозитория — зелено.

> **Правило:** `TMPDIR` для прогонов — на `/mnt/data`, но **за пределами рабочей копии**
> (например `/mnt/data/dev/.surge-verify-tmp`). Любой каталог внутри репозитория делает
> `SurgeConfig::discover()` находящим конфиг проекта, и тесты, которые полагаются на
> «конфига нет», падают с числами, выглядящими как настоящий дефект.

Отзыв находки здесь — правильное поведение ревьюера, а не промах: он перепроверил,
прежде чем оставить её в вердикте.

## Правка обоснования: проверяй место вывода, а не наличие честного текста (2026-09-06)

Найдено финальной сверкой таска 11. Форма повторяющаяся и легко проходит ревью.

Исполнителю указали, что комментарий оправдывает поведение ложной посылкой. Он дописал
честный текст **в модульный док и в док функции** — там теперь прямо сказано и про полный
проход по журналу, и про принятый долг. А ложная посылка уцелела ровно в той строке, из
которой делается вывод: «терминальный ран дешёвый, поэтому тянуть все раны безопасно».

Итог: файл противоречит сам себе, и следующий читатель, дойдя до места принятия решения,
получит старое, ложное основание — честный текст лежит на две сотни строк выше и до него
не дочитывают.

> **Правило:** правя обоснование, ищи **место, где делается вывод**, и правь его.
> Наличие честного описания где-то в файле дефект не закрывает. Проверять надо не
> «есть ли правдивый текст», а «на что опирается решение в точке, где оно принимается».

Смежное наблюдение того же круга: ограничение, названное **в отчёте исполнителя**, не
считается записанным. `record_heartbeat_success` намеренно не снимает окно ёмкости — это
было в отчёте, но grep по файлу давал ноль. Отчёт живёт в переписке, дока живёт в коде.

## Третий случай: комментарий описывает сценарий шире, чем закрывает код (2026-09-06)

Отдельная форма от «мёртвого кода» и от «фильтра не на том классе». Здесь вызов **есть**,
он на боевом пути, тест зелёный — но **не достижим из того сценария, который назван в
комментарии**.

| Круг | Что заявлено комментарием | Что покрыто на самом деле |
|---|---|---|
| 2 | `parse_retry_after` — «pure value extraction, sharing carries none of the risk» | возвращаемое значение и есть вход маршрутизации (`rate_limit_reset`) |
| 4 | `record_connect_failure` — «an agent whose **every** `connect()` attempt failed still reported `NeverObserved`» | покрыт только повторный connect в цикле промпта; холодный первый контакт идёт `CreateSession` → `create_session` → `validate_agent_auth` → `connect` и умирает на `?`, не касаясь трекера |

> **Правило приёмки:** проверяй не «есть ли вызов», а **достижим ли он из сценария,
> названного в комментарии**. Если комментарий говорит «каждый X», найди путь, на котором
> X происходит впервые, и проверь его отдельно от пути, на котором X повторяется.

Смежное, для меня как оркестратора: **ревьюер, отправленный до того, как правка легла,
вернёт её как незакрытую.** В круге 4 находка про `record_heartbeat_success` пришла
устаревшей — я отправил ревью раньше, чем исполнитель дописал док. Снимать такие находки
надо **проверкой файла**, а не спором с ревьюером и не переспрашиванием исполнителя.

## Таск 08 (перезапуск): вторая половина R21 закрыта — цена кросс-рановой корреляции (2026-09-06)

Условие таска 17 было: «либо кросс-рановый вход, отвечающий одним запросом к реестру, либо
явная запись цены перебора». Выбран **второй** вариант, осознанно, и вот почему первый не
взят.

**Почему не «один запрос».** Настоящий индекс потребовал бы денормализовать флаг эскалации
в `registry.sqlite`'s таблицу `runs`, записываемый оттуда же, откуда сегодня пишется
`EventPayload::EscalationRequested` (`surge-orchestrator::engine::stage::agent`). Но
писатель одного рана (`RunWriter`, `surge-persistence::runs::writer`) не имеет доступа к
пулу реестра вообще — единственный, кто сегодня пишет `registry.status`, это
`surge-daemon`/`surge-cli` через `registry::update_status`/`Storage::set_run_status`. Значит
настоящий индекс — это не правка в зоне таска 08 (`surge-cli/src/commands/memory.rs`,
`surge-persistence/src/memory/`), а новая схема плюс новый межкрейтовый путь записи через
демон — задача для отдельного таска, не для повторного запуска этого.

**Что построено вместо этого.** `surge_persistence::runs::list_loop_guard_stopped_runs(&Arc<Storage>, &[RunSummary])`
(`crates/surge-persistence/src/runs/escalations.rs`) — открывает `RunReader` и вызывает
уже проиндексированный `read_escalations` **для каждого рана из переданного среза**. Проход
per-run использует тот же `idx_events_kind`, что и одиночный `read_escalations`, — не второй
полный проход по журналу одного рана (это было бы регрессом к тому, что таск 17 уже закрыл).

Функция и `run_audit` не фильтруют раны по статусу до скана эскалаций — намеренно, по
факту о `RunStatus` выше в этом файле: ран, снятый guard'ом прямо перед смертью демона,
может остаться `Crashed`, а не `Failed`. Тест `run_audit_correlates_a_claim_with_a_loop_guard_stopped_run_even_when_the_registry_reads_crashed`
(`memory/audit.rs`) и его двойник на уровне настоящего бинарника
(`crates/surge-cli/tests/cli_memory_audit_test.rs`) строят ран именно в этом состоянии и
краснеют, если корреляция откатится к фильтру `status == Failed`.

`run_audit` сменил сигнатуру: `fn(&[MemoryClaim], &Pool<SqliteConnectionManager>) -> Result<AuditReport>`
→ `async fn(&[MemoryClaim], &Arc<Storage>, &Path) -> Result<AuditReport>`. Причина
асинхронности — не косметика: `Storage::open_run_reader` асинхронна по контракту
`surge-persistence::runs`, и разово открыть N ридеров без `.await` невозможно. Причина
смены `Pool` → `Storage`: одного пула реестра было достаточно для «раны со статусом
Failed» (прежняя половина R21), но не для «раны, чей журнал событий содержит эскалацию»,
для чего нужны per-run ридеры, а их выдаёт только `Storage`. Третий параметр, `project_root`,
добавлен на ревью этого перезапуска — см. пункт про локатор ниже. Оба вызывающих места
(`crates/surge-cli/src/commands/memory.rs::audit_memory`,
`crates/surge-orchestrator/tests/memory_writeback_test.rs::failing_run_records_a_claim_visible_to_the_audit`
— тест таска 07, доказывающий видимость аудиту, не переписан ни на что другое) переведены
на `.await` без изменения того, что каждый из них проверяет.

### Ревью этого перезапуска (2026-09-06): два блокера, оба сняты

Первый прогон гейта был зелёным, но ревью на настоящем бинаре нашло два блокера — оба
следствия того, что зелёные тесты проверяли компонент, не боевой вход (тот же класс, что
«Правило… доказывай достижимость» выше в этом файле).

**Блокер 1 — аудит писал в реестр.** `run_audit` брал раны через
`Storage::list_runs`, а тот (`storage.rs::Storage::list_runs`) зондирует pid каждого
`Running`/`Bootstrapping` рана и **пишет** `Crashed` через `registry::update_status` для
мёртвого. Замерено: строка ушла из `running`/`ended_at=NULL` в `crashed`/`ended_at=<ts>`
после одного `surge memory audit` — прямое нарушение контракта команды («аудит предлагает,
ничего не меняет сам»). Исправлено: `run_audit` берёт раны через
`crate::runs::registry::list_runs(&storage.registry_pool, &filter)` — то же поле пула,
тот же крейт, без зонда и без записи. Тест
`run_audit_never_mutates_the_registry_and_never_scans_a_run_no_claim_names`
(`memory/audit.rs`) вставляет ран с мёртвым pid и статусом `Running`, гоняет `run_audit`,
затем читает реестр напрямую и требует, чтобы статус остался `Running` — краснеет, если
`run_audit` вернётся к `Storage::list_runs`.

**Блокер 2 — один нечитаемый ран валил весь аудит.** `list_loop_guard_stopped_runs`
пробрасывала `open_run_reader`/`read_escalations` через `?`, и строка реестра без
пер-рановой директории (`OpenError::RunNotFound` — реальная форма, не гипотетическая: тот
же класс, что `surge-cli::commands::inbox::scan_run_capacity` уже обрабатывает как
best-effort) валила отчёт целиком, при нуле claim'ов. Исправлено: функция больше не
возвращает `Result` — она сама делает `match` на каждом ридере/чтении, логирует
`tracing::debug!` и складывает неудачный ран в `Vec<SkippedRun>` вместо `?`; `run_audit`
превращает каждый пропуск в запись `caveats`. Тест
`list_loop_guard_stopped_runs_skips_an_unreadable_run_instead_of_failing_the_scan`
(`runs/escalations.rs`) сажает рядом с рабочим guard-тронутым раном ран без директории и
требует, чтобы первый всё равно нашёлся, а второй попал в `skipped` — краснеет на откате к
`?`.

**Пункт 3, встроенный в тот же блокер-тест.** Скан теперь сужен до ранов, которых
**называет хотя бы один claim** (`run_id_from_source` по `transcript:`-локаторам), а не до
всего реестра — правка в `run_audit`. Тот же тест блокера 1 доказывает и это: «осиротевший»
ран не назван ни одним claim'ом, и если бы сужение не работало, попытка открыть его ридер
дала бы запись в `caveats` (`RunNotFound`) — тест требует `caveats.is_empty()`, значит
осиротевший ран не был даже тронут.

**Цена, названная раньше, была занижена по двум осям — поправлено.** `Storage::open_run_reader`
строит r2d2-пул (`max_size = StorageConfig::reader_pool_size`, по умолчанию **4**) плюс
фоновый `ScheduledThreadPool` пула — то есть один вызов `list_loop_guard_stopped_runs` на
N ранов открывает **до 4N SQLite-соединений и до 3N потоков-реаперов**, а не «N открытий».
Это конструкция самого `open_run_reader`, общая для всех вызывающих (включая
`surge-cli::commands::inbox`), — сужение до claimed-ранов (пункт 3) её не убирает, а
только уменьшает N. Фраза «единственная альтернатива — новая схема плюс межкрейтовый путь
записи через демон» была неверна ровно в этом смысле: для *этого* вызывающего дешёвый
рычаг — сузить N (сделано); убрать саму цену «пул на открытие» означало бы менять
`open_run_reader`, общий примитив многих вызывающих, — вне зоны этого таска.

**Локатор — существование решает относительно корня проекта, не CWD процесса.** До этого
раунда `classify_source`/`stale_claims` проверяли существование и читали файл относительно
CWD аудита — один и тот же claim классифицировался `FilePath` из одного каталога и `Url` из
другого (хуже обычной ошибки: путается **вид**, не только вердикт устаревания). Исправлено:
обе функции берут `project_root: &Path`, и `resolve_against` анкерит любой относительный
путь к нему (абсолютный путь и путь из `file:` URI остаются как есть). CLI резолвит корень
через `surge_git::GitManager::discover()` (тот же способ, что `surge project describe` уже
использовал — перенесено в `commands::common::project_root`, общий helper). Тест
`ambiguous_colon_prefixed_path_that_exists_is_treated_as_a_file_not_a_url` прогоняет один и
тот же claim через два разных `project_root` и требует разные вердикты — доказывает, что
решает корень, а не CWD.

**Percent-encoding в `file:` URI.** `file:///a%20b.txt` раньше резолвился по
буквальному (закодированному) тексту — `NotFound` на файл, который на самом деле есть,
превращался в ложный `SourceMissing`, худший исход для инструмента, чей выход — предложение
удалить. Исправлено: `file_uri_to_path` отказывается разбирать путь с `%` в теле,
пропуская его в обычную двусмысленную ветку (`unverifiable`, не `stale`). Тест
`file_uri_with_percent_encoding_is_reported_unverifiable_not_falsely_missing`.

**Claim на ран, которого нет в реестре, раньше молча выпадал.** `run_statuses.get(&run_id)?`
внутри `filter_map` ронял такой claim без следа. Исправлено: `run_audit` отдельно проверяет
каждый `claimed_run_id` против `run_statuses` и кладёт по нему запись в `caveats`, если
рана нет. Доку `AuditReport::caveats` («fully computed») поправлена — поле честно называет
оба случая, которые в нём теперь появляются.

**`SourceKind::Unrecognized` был недостижим.** `is_file_path`'s (`has_explicit_path_marker`
теперь) финальная ветка и второй scheme-чек в `classify_source` были одной и той же
проверкой дважды — вариант `Unrecognized` не мог возникнуть ни на одном входе. Убран вместе
с мёртвым плечом `match` в `stale_claims`; классификация теперь исчерпывающий `match` без
тавтологии.

**`$SURGE_HOME` в тестовой изоляции.** `project_context.rs::with_home` перекрывал только
`$HOME`; после того как `MemoryStore::default_path()` в этом же перезапуске научился
уважать `$SURGE_HOME` первым, тест с уже выставленным в окружении `$SURGE_HOME` писал в
реальный, общий стор, оставаясь зелёным. Исправлено: `with_home` теперь снимает и
`SURGE_HOME` на время `f`, восстанавливая оба после. Тест
`with_home_isolates_even_when_surge_home_is_already_set_in_the_environment`
(`project_context.rs`) выставляет `SURGE_HOME` снаружи `with_home` и требует, чтобы путь
стора остался под throwaway `HOME`, — краснеет на откате.

Также закрыты три хвостовых долга из раздела «Долг для повторного запуска» в
`08-memory-audit.md`: (1) утверждение на `C:/Users/...` с прямыми слэшами добавлено в тот
же тест, что уже проверял `C:\Users\...`; (2) `file:///path` разворачивается в путь и
проверяется как обычный файл; юникс-путь с похожей-на-схему первой частью
(`my:notes/file.md`) решается **существованием на диске** (относительно `project_root`, не
CWD — см. выше), а не формой строки; (3) `MemoryStore::default_path()` теперь читает
`$SURGE_HOME` (было: только `dirs::home_dir()`), выровнено с `surge_home_dir()` (CLI) и
`pidfile::daemon_dir()` (демон). `ArtifactStore::default_path` и `Store::default_path`
(`crates/surge-persistence/src/{artifacts,store}.rs`) несут тот же разрыв и не тронуты —
вне зоны этого таска, записано в доке `MemoryStore::default_path`, чтобы следующий не
открывал заново.

## Обоснование может протухнуть от чужой правки (2026-09-06)

Найдено при планировании таска 12. Форма отличается от «комментарий шире кода»: здесь
комментарий был **верен, когда писался**, и следующий коммит делает его ложным.

Таск 11 оставил в `RATE_LIMIT_PATTERNS` образец `overloaded_error` — это Anthropic 529,
**перегрузка сервера**, а не исчерпание квоты. Широта была узаконена явным доводом
(`health.rs:336-344`): «over-inclusion here only changes what an operator is **shown**,
not a routing decision». На тот момент — правда.

Таск 12 делает **тот же классификатор** драйвером парковки рана. Довод перестаёт
действовать, и если его не переписать в том же коммите, следующий человек дошьёт новый
образец, опираясь на посылку, которой больше нет.

> **Правило:** обоснование вида «это безопасно, потому что ни на что не влияет» —
> **условное**. Меняя потребителя так, что он начинает влиять, перепиши обоснование
> **в том же коммите**. Грепом такое не ищется: искать надо по вопросу «на чём держалась
> широта того, что я теперь подключаю к поведению».

## Латентный дефект оживает от нового вызывающего (2026-09-06)

Найдено ревью M0 таска 12. Форма отличается от всего, что мы ловили: код **не менялся**,
а стал опасен.

`surge_core::capacity::parse_retry_after_secs` ищет маркер в приведённой к нижнему
регистру копии и нарезает **оригинал**. Символ, чей нижний регистр другой длины в байтах
(`İ` U+0130 → 3 байта), сдвигает смещения, и срез паникует на границе символа.

Дефект был там всё время. Но до M0 у функции не было вызывающих в `surge-acp`, и её вход
никогда не приходил извне. M0 подключил её к пути, где текст приходит **от агентского
рантайма**, и где `send_message_impl` ожидается инлайном в `bridge_loop` — единственной
задаче, обслуживающей **все** сессии. Падает не ран, падает мост.

> **Правило:** заводя нового вызывающего для существующей функции, проверяй её **на
> недоверенном входе**, даже если сама функция не менялась. Вопросы: откуда теперь
> приходят её аргументы, и что она делит с другими — поток, цикл, соединение.

Смежное из того же ревью: `#[non_exhaustive]` **заставляет** wildcard, а wildcard делает
будущий вариант молчаливым. Ставить метку стоит только там, где каждый потребитель может
безопасно свалить незнакомый вариант в одну корзину — лог, отображение. Там, где разные
варианты обязаны вести к разному поведению, отсутствие метки и есть защита: компилятор
заставит каждое место решить.

## Почему гейт не ловит недостижимый код, и что с этим делать (2026-09-06)

Шестой случай дефекта достижимости за прогон дал наконец **объяснение механизма**, а не
очередное правило.

`parse_reset_hint` была написана, задокументирована и покрыта восемью зелёными тестами —
при нуле боевых вызывающих. Старый путь (`from_observed_error`) продолжал звать прежнюю
функцию. Доказано напрямую: новая возвращает `Some(now+30s)` на теле Google, а окно
ёмкости получает `None`.

**Почему ни клиппи, ни тесты этого не видят:**

- `pub`-функция в библиотечном крейте **не даёт предупреждения о мёртвом коде** — она
  часть публичного API, и компилятор обязан считать её используемой;
- тесты зовут её **напрямую**, поэтому набор не может заметить, что больше её не зовёт
  никто.

То есть зелёный гейт здесь не слабый — он **структурно неспособен** увидеть дефект.

> **Обязательный шаг приёмки:** для каждой новой `pub`-функции или метода — грепнуть
> **боевых, нетестовых** вызывающих, **прежде** чем принимать любое утверждение о её
> поведении. Ноль вызывающих означает, что заявление «теперь работает X» неверно
> независимо от того, сколько тестов зелены.

Прецеденты в этом репозитории: `parse_reset_hint` (таск 12, M1); `AgentPool::record_failure`
и вся ёмкость в `HealthTracker` — построены и покрыты, а на пути движка не исполняются
никогда.

## Мутационная проверка находит то, чего чтение не находит (2026-09-06)

Ревью M1 применило приём, который стоит взять в постоянный оборот: **испортить код и
посмотреть, покраснеет ли набор.** Две дыры, невидимые при чтении:

- поднять ветку слепого бэкоффа выше правила «наблюдённый сброс важнее догадки» — **все
  13 тестов правил остаются зелёными**. Несущая половина порядка, который дока называет

- инвертировать ветку «исчерпано + истёкший сброс + бэкофф задан» — **весь набор из 674

## `#[non_exhaustive]` делает исчерпывающий кросс-крейтный match невозможным (2026-09-06)

Ошибка **оркестратора**, и вдвойне обидная: правило было выведено в этом же прогоне, а
через три этапа я потребовал того, что оно запрещает.

На ревью M2 я велел «удалить хвостовой `_ => {}` в `views.rs`, перечислить все варианты, и
тогда компилятор начнёт обеспечивать то, что обещает комментарий». Ревьюер это же и
предлагал. **Оба не проверили.**

`EventPayload` помечен `#[non_exhaustive]` в `surge-core`, поэтому `match` по нему из
другого крейта **обязан** нести wildcard — `E0004`, сколько вариантов ни перечисли.
Удаление невозможно по устройству языка.

Это прямое следствие правила, записанного выше в этом же файле: **метка заставляет
wildcard, а wildcard делает будущий вариант молчаливым.** Метка на `EventPayload` — верное
решение (варианты добавляются часто, и внешние крейты не должны ломаться), но она же
навсегда лишает внешних потребителей защиты компилятора.

**Что работает вместо этого** (сделано исполнителем и проверено эмпирически): перечислить
все известные варианты явно, а телом обязательного wildcard поставить
`debug_assert!(false, "…")` вместо `{}`. Тогда провалившийся вариант **паникует в тестах**,
а в релизе деградирует в безопасный no-op. Проверка: вернуть вариант в wildcard — тест
обязан упасть.

**Но это растяжка времени выполнения, а не проверка компилятора, и дыра в ней настоящая.**
Я сначала записал, что assert даёт то же, что дал бы классификатор внутри `surge-core`, —
**это неверно**, и ревью поправило. Assert срабатывает, только когда вариант **реально
доходит** до функции в отладочной сборке. Доказательство: **он не поймал бы M1** — до теста,
написанного на M2, `RunParked` в `maintain` не скармливал никто. И три варианта
(`BootstrapArtifactProduced`, `BootstrapStageStarted`, `StageInputsResolved`) не
конструируются в воркспейсе **нигде**: «вариант существует» ≠ «вариант доходит».

Классификатор, живущий в `surge-core`, был бы **проверен компилятором** — внутри
определяющего крейта метка не действует, и это единственное место, где исчерпаемость по
`EventPayload` вообще достижима. Отклонён он по другой причине: `surge-core` пришлось бы
знать о существовании нижележащих материализованных вью — протечка слоёв ради одного
`match`.

> Записывать такие решения надо как **«принята растяжка с известной дырой по названной
> цене»**, а не «дыра закрыта». Разница всплывёт ровно тогда, когда следующий вариант
> провалится молча.

> **Правило:** прежде чем требовать исчерпывающий `match`, посмотри, не помечен ли тип
> `#[non_exhaustive]` **и из своего ли он крейта**. Внутри крейта метка не действует,
> снаружи — делает требование невыполнимым.

## Не требуй красный-до-зелёного там, где «красное» и есть вред (2026-09-07)

Ошибка **оркестратора**, стоившая загрязнения личного файла пользователя **дважды**.

Тесты движка писали записи памяти в настоящий `~/.surge/memory.db` разработчика: конфиг
без явного пути → `record_node_failure` → `MemoryStore::default_path()`. Утечку нашли,
закрыли в восьми местах, файл вычистили.

Затем обнаружилась латентная дыра: `resume_run` пересобирал конфиг с нуля и путь терял.
Я потребовал закрыть её **с доказательством красный-до-зелёного**.

Но «красное» состояние этого теста — это буквально «запись уходит в реальный стор».
Чтобы предъявить красноту, исполнитель отключил фикс и прогнал тест — и **воспроизвёл
ровно тот вред, который мы убирали**. Он сделал всё остальное правильно: снял копию,
опознал строку, немедленно вернул фикс, попытался удалить, упёрся в запрет прав, **не стал
его обходить** и доложил.

> **Правило:** прежде чем требовать красный-до-зелёного, спроси — *что произойдёт, пока
> тест красный?* Если ответ затрагивает состояние **вне** рабочей копии — файлы
> пользователя, внешние службы, общие ресурсы, — красноту надо предъявлять на
> **изолированном дубле**, а не на боевом пути. Либо принять доказательство другой формы:
> мутацию в юните, разбор кода, отсутствие вызывающего.

Смежное: у теста, чьё «красное» состояние необратимо, красный-до-зелёного вообще не
является допустимым доказательством. Требовать надо **свойство**, а не ритуал.

## Одна фикстура сертифицирует одно поле, а не рендерер (2026-09-07)

Найдено мутацией на ревью таска 09, и это самая наглядная демонстрация приёма за прогон.

`escape_html` применялся в **пятнадцати** местах рендерера. Мутация удалила **четырнадцать**
из них — и **28 из 28 тестов остались зелёными**. Единственный тест на экранирование
кормился фикстурой всего с двумя событиями, то есть закреплял ровно одно поле.

Живой уязвимости не было: в поставленном коде экранирование стояло везде. Но его
исчезновение не заметил бы никто.

> **Правило для любого рендерера, принимающего недоверенный вход:** тест обязан кормиться
> фикстурой, кладущей разметку (`<script>`, `"`, `&`) в **каждое** поле-строку, которое
> может дойти до вывода, и утверждать посекционно. Тест на одно поле доказывает
> экранирование **одного поля**, а не рендерера.

Смежное, из того же ревью: три места в репозитории — дока функции, ADR и CHANGELOG —
утверждали «каждое динамическое значение экранируется». Пять интерполяций не
экранировались и были безопасны лишь потому, что их типы валидированы или не строки.
**Инвариант, на котором держится безопасность, не был назван нигде.** Утверждение в
трёх местах при отсутствии проверки в одном — хуже, чем отсутствие утверждения.

## Проекция над `EventPayload` не имеет права на `_ => {}` (2026-09-07)

Отчёт о ране — проекция журнала — терял **26 из 57** вариантов в хвостовой ветке, включая
`RunStarted` (то есть саму формулировку задачи), `EscalationRequested` (причину остановки)
и `OutcomeRejectedByHook` (отвергнутый исход рендерился как принятый).

Ключевое отличие от случая с `views.rs`, где wildcard **обязателен**: там `match` идёт из
чужого крейта, и `#[non_exhaustive]` делает исчерпаемость невозможной. Здесь проекция
живёт **в `surge-core`**, то есть в определяющем крейте, где метка не действует, —
исчерпывающий `match` достижим и обязателен.

> **Правило:** прежде чем принять `_ => {}` в проекции над `EventPayload`, проверь, из
> своего ли ты крейта. Внутри — писать явные пустые армы под комментарием «намеренно не
> в отчёте», чтобы следующий вариант потребовал решения. Снаружи — `debug_assert!`
> вместо пустого тела, и запись «принята растяжка с известной дырой».

## Экранирование принадлежит стыку, а не рендереру (2026-09-07)

Ошибка **оркестратора**: я велел «экранировать markdown», и это оказалось категориальной
путаницей.

Отчёт о ране имеет два выхода: терминал (`surge run report --format md`, дока рендерера
прямо говорит «readable in a terminal, an archived .md file») и комментарий трекера, где
он оборачивается в `<details>` и рендерится как HTML. Исполнитель применил `escape_html`
**внутри рендерера** — и терминальный вывод испортился: `don't merge until Bob's "final"
review & CI pass` печатается как `don&#39;t merge until Bob&#39;s &quot;final&quot;
review &amp;amp; CI pass`.

`escape_html` экранирует `' " &` — это **атрибутное HTML-экранирование**. Для markdown-
документа оно не «слишком строгое», а **не то по природе**.

> **Правило:** экранирование принадлежит **стыку с приёмником**, а не производителю
> документа. Один рендерер с двумя выходами обязан отдавать дословный текст, а обёртка
> под конкретный приёмник экранирует под его правила. Иначе один потребитель чинится
> ценой порчи другого.

**И вторая половина, которую HTML-экранирование не закрывает вовсе.** Свободный текст,
пришедший от третьей стороны (`initial_prompt` — из тела тикета), несёт **markdown-
структуру**: перевод строки, `##`, `- **bold**`. Вставленная туда поддельная секция
«Verifier verdicts … VERIFIED» встаёт **выше настоящей**, при `evidence_backed = Some(false)`.
Экранирование HTML-сущностей от этого не защищает — нужна либо однострочная нормализация,
либо markdown-экранирование заголовков, переводов строк и `|`.

**Как это осталось незамеченным:** XSS-фикстура содержит `"quo'te"`, но ассерты проверяют
только появление `&lt;script&gt;`. Теста «обычная пунктуация переживает рендер» не было —
поэтому порча терминального вывода была зелёной.

## Знаменатель расходится тише, чем квантор (2026-09-07)

Требование «три поверхности отвечают одинаково» проверялось на кванторе (`any` против
`all`) и было починено. Расхождение осталось — **в знаменателе**.

Отчёт считает по задачам, **эмитнувшим вердикт-событие**; инбокс — по **всем строкам**
`task_ledger_index`. `TaskDiscovered` создаёт строку леджера **без вердикта**, поэтому на
одном ране: отчёт `Some(true)`, инбокс `Some(false)`, леджер «2 задачи, 1 проверена».

**Фикстуры это скрывали:** обе стороны имели по пять элементов, знаменатели случайно
совпадали.

> **Правило:** сверяя два агрегата, сверяй **множество, по которому идёт счёт**, а не
> только операцию над ним. Фикстура с равным числом элементов с обеих сторон делает
> расхождение знаменателей невидимым по построению.

Смежное, из того же круга: починка «вердикты не отзываются» была сделана **удалением**
записи, тогда как эталонный фолд её **оставляет** с `verified=false`. В сочетании с `all()`
это выбрасывает провалившуюся задачу из знаменателя и **поднимает** агрегат — два верных по
отдельности фикса дали ложное «доказано».
