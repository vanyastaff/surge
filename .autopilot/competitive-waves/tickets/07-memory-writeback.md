## Что должно заработать

Память пишется на границе рана как исход ноды, а не как побочный эффект где-то в середине. В неё едет корневая причина цепочки, а не последняя ошибка; если запись по теме уже есть — она обновляется на месте, а не дублируется почти-копией. Чистый ран не пишет ничего. Фоновое старение трогает только непроверенные записи.

## Из брифа, дословно

> «**Write-back discipline** at run boundaries … root cause over symptom, update in place over near-duplicate, silence on a clean run, and never on the agent's own initiative — a memory write is a node outcome, not a side effect»
> «it now also ages only *eligible unverified* entries, never verified ones»

## Критерии приёмки

- [ ] Запись в память — исход ноды; агент не может инициировать её сам
- [ ] Записывается корневая причина цепочки, а не последняя ошибка
- [ ] Перед созданием ищется покрывающая запись; найдена → обновление на месте
- [ ] Ран без находок не пишет ни одной записи
- [ ] Старение трогает только eligible `unverified`; `verified` не стареет никогда
- [ ] **Локатор источника — по контракту из `interfaces.md`**, раздел «Контракт локаторов памяти»: либо путь к файлу репозитория, либо `transcript:run-<ULID>#turn-N`. Своя форма означает, что аудит (таск 08) не найдёт эти записи никогда — он не упадёт и не пожалуется, он просто останется пустым
- [ ] Тесты: чистый ран, дубликат, попытка состарить проверенную запись, **и запись, произведённая этим таском, реально видна аудиту таска 08**

### Что оказалось неверным в обосновании исполнителя

Заявлено: «всё, что `body` спавнит, к моменту восстановления уже завершено». Ложно трижды:
`handle.await_completion()` (`handle.rs:80-84`) ждёт один рантаск, а не джойнит всё;
блокирующий пул tokio держит треды ещё `KEEP_ALIVE = 10s` после завершения задачи и не
джойнится; r2d2 крутит собственный reaper-тред вне tokio. Плюс в
`failing_run_records_a_claim_visible_to_the_audit` `storage` намеренно жив **после**
восстановления.

Заявленный прецедент (`project_context.rs:1505-1533`) покрывает **только синхронный**
случай — все три его вызова из `#[test]`, и его SAFETY прямо оговаривает «spawns no
threads». Про асинхронный он молчит, следовательно ничего про него не разрешает.

### Механизм — записан, потому что интуиция здесь обманывает

Гонку создаёт **не** `realloc` массива `environ`: glibc реаллоцирует, только когда имени
в массиве нет, а `HOME` есть. И **не** `tempfile`/`std`/tokio — все Rust-читатели
сериализованы через `ENV_LOCK` (`sys/env/unix.rs:67,113,132,140`).

Гонят **вендоренные C-читатели в том же бинарнике**: libgit2 `git__getenv` — голый
`getenv(name)` (`util.c:786-788`) — вызывается **с `"HOME"`** (`sysdir.c:357,405`);
бандленный SQLite читает `TMPDIR` (`sqlite3.c:44352-44353`). `getenv` сканирует весь
массив, поэтому читатель **любой** переменной делает загрузки тех же слотов, куда
`setenv` пишет.

### Решение: вариант B — убрать зависимость от окружения

Путь до стора проводится явным опциональным полем конфига; `MemoryStore::default_path()`
остаётся дефолтом при пустом поле. Все шесть `unsafe` из файла исчезают, вместе с UB и
с записью в реальный стор. Отклонены: мьютекс + `test-group` и `current_thread`-рантайм —
оба сужают окно, но оставляют код несостоятельным (блокирующий пул даёт настоящие
OS-треды и при `current_thread`); ре-exec в дочерний процесс — строит харнесс ради обхода
проблемы, которую вариант B удаляет.

### MIRI-SKIP — структурно, а не по стоимости

miri не исполняет чужой машинный код, а `rusqlite features=["bundled"]` и `libgit2-sys`
вендорят C. Замена для этого класса — TSan (`RUSTFLAGS=-Zsanitizer=thread`).
