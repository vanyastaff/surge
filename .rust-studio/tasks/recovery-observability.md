# Stage B — recorded recovery observability contract (draft for maintainer precode)

Read-only design; no code/tests/Cargo/provider/original-fixture changes. Main inspected at a2ba09c. Separate new runtime bug scope; Home/harness3/3 budgets unchanged. Stage A graph-authority repair is separate and does not by itself close these UI/daemon defects.

## Selected contract

A durable RunRecoveryRequired is a recorded, nonterminal operator-attention fact. It does not mean RunFailed, RunCompleted, provider settlement, a fresh gate answer, or retry authorization. Its existing diagnostic remains owned by the run journal. Bootstrap status stores only the finite reason and exact existing run/phase, never a second diagnostic or authority record.

Use one additive BootstrapAttentionReason::RecoveryRequired (serde recovery_required). Supervisor emits it only for a successfully tracked/matching RunOutcome::RecoveryRequired. Actual TrackingError, storage read/write failure, OutcomeMismatch and SettlementFailed continue to mean unconfirmed, not this confirmed refusal category.

The UI must separately represent (a) recorded recovery problem and (b) current observation availability. Known problem history must remain inspectable while its current result/cleanup is unconfirmed. In particular, old NeedsAttention(StorageUnconfirmed)+durable142 must show the recorded diagnostic without claiming disk exhaustion or upgrading unknown settlement to confirmed recovery completion.

No new runtime action, poller, event transport, scheduler, automatic retry, receipt backend or compatibility shim is proposed.

Lifecycle rule, reshaped after maintainer source review:

Numeric generation is not an ownership classifier. RunMemory defaults to generation0, and WorkItemAttemptBound sets the actual work_item binding without changing that counter (run_state.rs675 and1730). An initially controlled WorkItem can therefore fail at generation0. Never equate generation0 with bootstrap or absence of control.

The existing source settles the bounded policy without a new runtime marker:
- Replayed admission explicitly calls resume(run_id, worktree, None, None), after refusing a reserved task (engine/admission/mod.rs293–295). This is the existing uncontrolled ordinary-run path, not a bootstrap-only policy.
- TaskResume validates the WorkItem claim and obtains Continue evidence from the durable execution control (admission/mod.rs297–332).
- Bootstrap supervisor uses TrackingContext.resume for an existing run. Neither generic nor bootstrap resume universally emits RunContinued.
- RunContinued is written by restored reserved continuation (run_task.rs263–375) or the agent's actual ContinueReserved path (stage/agent.rs1339–1348). The memory's existing strict-greater-generation acceptance is the continuation predicate; Stage B does not relax it.

Recommended observational rule:
1. Retain the latest recorded RecoveryRequired strictly by event sequence, including its diagnostic and recorded generation. This observational capture is independent of the guarded control_generation accumulator: a later lower-generation recovery still becomes the latest problem and remains visible; it cannot silently disappear merely because its generation was not accepted for control state. Keep older diagnostics in the existing journal/log. A newer RecoveryRequired replaces the latest problem and resets any prior supersession marker. A higher RecoveryRequired, RunSuspended, general control_generation change, subscription, phase/status, materialization, retry click or elapsed time does NOT clear the problem.
2. Record presentation supersession only in the existing accepted RunContinued branch (strictly increasing generation), at that exact event sequence. Reuse the existing predicate; do not infer continuation from a later generation value in some other event.
3. A later StageEntered can instead demonstrate observed progress only for a complete, contiguous, known-unbound run: memory.work_item is None in a trusted full prefix. This policy applies to existing uncontrolled ordinary and legacy bootstrap execution alike; pure core has no bootstrap-operation identity and must not invent one. It means only that a later stage was recorded, never that a retry was authorized, a process is currently alive or cleanup settled. It is insufficient to assert Working without independently available current observation.
4. A WorkItem-bound run, including generation0, cannot supersede recovery on StageEntered. It requires the existing accepted RunContinued event. A torn/missing prefix, a gap or unavailable source cannot establish absence of a binding; such consumers keep current state unknown and retain the diagnostic as history. Existing TaskExecutionView/source coverage fences are mandatory.
5. Terminal remains terminal-first. Preserve the latest problem as history after observed progress or a terminal verdict. A subsequent recovery starts a fresh blocked interval at its own sequence. Do not compare only max(stage_occurrences) with a stored generation or reuse a stale supersession marker.

The minimal representation may keep the last recovery plus an optional exact accepted-continuation supersession sequence, and use existing stage occurrence order only when the trusted view proves no WorkItem binding. Alternatively an explicitly typed observational supersession marker is acceptable. It must be updated within the same RunMemory seam and reused by RunDisplay/TaskExecutionView; no independent UI event-order algorithm. The marker is a presentation observation and is never consumed by runtime admission/control.

Required tests: WorkItemAttemptBound + recovery at generation0 + laterStageEntered remains blocked; the same binding with accepted strict-greater RunContinued supersedes; stale/equal Continue does not; unbound ordinary and bootstrap-shaped complete runs can show later recorded progress; partial/gapped absence of binding cannot; higher recovery/suspension generation cannot clear; two recovery events, including a later lower-generation record, select the latest seq/diagnostic and reset earlier supersession; later accepted Continue/progress affects only the latest blocked interval. ## Serialized observation clarification — bounded API amendment

Source facts: TaskExecutionView derives Serialize/Deserialize (task_execution.rs250) and currently has no recovery field. RunReport.task_execution is already defaulted Option (run_report/mod.rs160): an old report without the entire projection becomes None. However an old serialized report that contains an old TaskExecutionView needs a separate unknown state inside that projection. Compile currently detects envelope sequence gaps, including a first seq greater than1 (compile.rs28), but it does not require event1 to be RunStarted. Therefore absence of PartialJournal caveats alone is insufficient to establish known-unbound ownership. Existing consumers compile events directly; roundtrip report tests at task_execution/tests.rs549–553 exercise the actual serialized path.

Proposed smallest field/type shape (illustrative Rust, not implementation):

```rust
#[derive(Debug, Clone, PartialEq, Default, Serialize, Deserialize)]
#[serde(tag = "observation", rename_all = "snake_case")]
pub enum RecoveryObservation {
    #[default]
    NotLoaded,
    CompletePrefix {
        through: u64,
        latest: Option<RecordedRecoveryRequired>,
    },
    PartialPrefix {
        through: Option<u64>,
        latest: Option<RecordedRecoveryRequired>,
    },
}

// Inside existing TaskExecutionView:
#[serde(default)]
pub recovery: RecoveryObservation,
```

Serialized distinctions:
- Old missing field -> NotLoaded -> serialize explicitly as `{"observation":"not_loaded"}`. It never means recovery was inspected and absent.
- Fresh complete journal prefix with no recovery -> `{"observation":"complete_prefix","through":140,"latest":null}`.
- Fresh complete prefix with recovery -> same complete_prefix object with latest recorded seq/generation/bounded diagnostic and its already-reviewed observational supersession information.
- Torn/gapped prefix -> `{"observation":"partial_prefix","through":142,"latest":...}`; latest is inspectable history, never a proven current absence/known-unbound state.
- Empty supplied slice -> partial_prefix with through:null and latest:null. Empty data is not a complete run prefix.
- Old report with no task_execution -> existing None behavior, outside this field.

CompletePrefix means supplied envelopes begin at seq1 with RunStarted and are contiguous through the recorded through value. It does NOT mean EOF, atomic source snapshot, current freshness, available transport, settled processes, or runtime authority. Consumers must still apply their independent loading/availability/current-observation fences. No runtime control reads this field. No new all-purpose source coverage system is required; reuse existing gap detection and add only the RunStarted-at-first-envelope check necessary for this recovery/ownership observation. Partial must remain partial after any gap, even if later StageEntered exists. Bound generation0 still uses accepted Continue regardless of coverage.

Do not use Option<Option<T>>: ordinary serde missing and null handling would obscure the intended contract, while this explicit tag roundtrips it. Do not use skip_serializing_if on NotLoaded: explicit output helps callers retain the unknown distinction. Explicit null for the entire recovery field or an unknown observation tag must reject, rather than silently becoming confirmed absence. Deserialize remains a readonly report representation, never authority to launch/continue/retry. A manually supplied readonly report cannot prove authenticated runtime ownership; runtime consumers use fresh journal compilation, not report deserialization.

API consequences: one new public readonly enum and one defaulted field replace the previously underspecified optional recovery field; no extra report field, RunCompletion variant, transport message or CLI/operator signature. TaskExecutionView struct literal initializers must set the new field (the production initializer is compile.rs63). Existing JSON readers ignoring unknown fields continue reading new reports, while new readers can read old projections explicitly as NotLoaded. Older readers do not gain recovery semantics; no forward semantic compatibility is claimed. This concrete shape should be covered by the affected maintainer/API check, but it does not expand the accepted recovery contract or source write zone.

Required exact tests: deserialize an actual old RunReport JSON containing task_execution but with recovery omitted -> NotLoaded; an old report omitting task_execution -> None; new complete no-recovery -> CompletePrefix/latestNone; complete with recovery -> latest exact seq and roundtrip; missing RunStarted despite seq1 contiguous -> PartialPrefix; first seq>1/gap -> PartialPrefix with retained latest; empty slice -> PartialPrefix/None; serialize-deserialize each tagged state without collapse; whole-field null/unknown tag rejects; report and desktop never label NotLoaded or PartialPrefix as confirmed no-recovery/current Working. Existing malformed-envelope compile errors retain RunReport.task_execution=None and its existing unavailable caveat.
