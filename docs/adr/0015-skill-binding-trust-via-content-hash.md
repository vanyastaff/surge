# ADR 0015 — Skill binding: content hash is the trust boundary, reusing the profile-trust approval form

## Context

A flow node can declare skills it wants an agent to have (`AgentConfig::declared_skills`, read from `custom_fields["skills"]` as a list of `surge_core::skill::SkillRef`). A skill pack is third-party, executable-shaped context: its instructions steer the agent the same way a system prompt would, and — per [ADR-0002](0002-profile-trust-deferred.md) — Surge already treats a profile's tool/sandbox declarations as the same class of risk. `SkillCatalog::resolve` (Task 02) always re-reads and re-hashes a pack from disk at bind time, deliberately uncached, so a pack swapped between discovery and use is visible rather than served stale. What was left open, and is the subject of this ADR, is: what makes a resolved skill *trusted enough to bind without asking*, and what happens when it isn't.

> **Correction (2026-09-06, post-review).** The first pass of this delivery built the sequence below exactly as decided — resolve, compare, gate, emit `SkillBound` — but built it against **two dead ends**: `ResolvedSkill::instructions` was resolved and discarded (the agent never saw the skill's content), and the approval round trip below used `EventPayload::ApprovalRequested`/`ApprovalDecided`, which no surface renders (`cockpit::dispatch::decide_action` and `surge inbox` both key off `HumanInputRequested`; `pending_approvals` has no reader outside `surge-persistence`). In production, an unpinned skill's approval was a silent timeout every time, and a trusted skill's instructions never reached the agent even when binding "succeeded." The paragraph below is corrected to what actually ships: the approval round trip is `HumanInputRequested` / `HumanInputResolved` / `HumanInputTimedOut` — the path the cockpit and inbox already render — and `bind_skills` returns each bound skill's resolved instructions so the caller (`engine::stage::agent`) appends them to the system prompt. `SkillBound` additionally carries the node explicitly (not positional inference) and a `gate_enabled` flag recording whether `ApprovalConfig::skill_approval` was active for that bind. The trust *policy* (hash-pin comparison below) is unchanged from the original decision — only the delivery mechanism was wrong.

> **Correction 2 (2026-09-06, second review pass).** Measured against the real `~/.claude/plugins` corpus (352 `SKILL.md`, all under `plugins/` — `~/.claude/skills` is empty, correcting an earlier formulation that named both directories for one combined count), 49 of 99 skill names have more than one physically distinct, differently-hashed pack. `bind_skills` resolved every declared skill by stripping the pin to `hash: None` first (to detect drift), which meant an **unpinned** declaration of one of those 49 names hit `SkillError::Ambiguous` and failed the node with `StageError::SkillResolutionFailed` **before ever reaching the approval gate below** — for roughly half the corpus, the promise "an unpinned skill requires explicit approval" was simply false; it required nothing, because the node never started. Fixed: a `hash: Some(pin)` declaration now resolves directly against that pin first (`SkillCatalog::resolve` narrows a `Some(hash)` lookup to identical content, so this path cannot itself be ambiguous); only a `None` declaration, or a pin that no longer matches anything (`NotFound`), falls back to the name/provider(/version)-only lookup where `Ambiguous` is treated as approval material, not a failure — every current candidate's hash goes into the prompt, and the lexicographically smallest is what binds if approved. Two further fixes landed in the same pass: `SkillCatalog::discover`'s synchronous filesystem walk-and-hash now runs via `tokio::task::spawn_blocking` and is cached once per run (not re-walked on every node), and `ApprovalConfig::skill_approval` now also falls back to the resolved profile's value, not only a node's own override.

## Decision

**A skill binds without a prompt only when the node's declaration pins the exact content hash the catalog resolves right now.** Concretely, for each declared `SkillRef`:

1. Resolve it against the catalog by **name, provider, and version only** — never by the declared hash. (`SkillCatalog::resolve` treats a `Some(hash)` as *narrowing the search to that exact content*, which is right for a caller that wants one specific pack among several candidates, but wrong for a trust check: it would turn "the pack drifted" into `NotFound` instead of a comparison.)
2. Compare the declaration's `hash` field against the freshly-resolved `ResolvedSkill::hash`:
   - `hash: None` (unpinned/unhashed) → **always requires approval.** There is nothing on record for the operator to have already blessed.
   - `hash: Some(h)` and `h != resolved.hash` → **requires approval.** The pack changed since whoever wrote `h` looked at it; approving silently would be exactly the silent-swap ADR-0002 already refuses for profiles.
   - `hash: Some(h)` and `h == resolved.hash` → **binds immediately**, no prompt. The declaration is itself the operator's prior sign-off on this exact content.
3. Every skill that ends up bound (whether trusted immediately or approved this run) appends `EventPayload::SkillBound { node, name, provider, hash, gate_enabled }` — the hash actually resolved, not the stale pin, and the node it bound onto explicitly — so a full replay of the event log reconstructs exactly which skill, at which content, entered which node, with no dependency on positional inference or out-of-band state. `bind_skills` also returns each bound skill's resolved instructions to the caller, which appends them to the agent's system prompt before the session opens (see Correction above) — `SkillBound` records that a skill *was* bound; it does not, by itself, deliver anything to the agent.

**The approval round trip reuses the engine's existing node-keyed decision path**, not a new one: it registers into the same `gate_resolutions` map and is resolved through the same `Engine::resolve_human_input` entry point a `HumanGate` node's operator response already goes through, and it emits `HumanGate`'s own `EventPayload::HumanInputRequested` / `HumanInputResolved` / `HumanInputTimedOut` events — the path `cockpit::dispatch::decide_action` and `surge inbox` already render — rather than the `ApprovalRequested` / `ApprovalDecided` pair (see Correction above: that pair has no renderer anywhere, so using it was building a second, undelivered approval path while believing it reused the first one). This does **not** emit a synthetic `OutcomeReported` for the node: only `HumanInputRequested`/`HumanInputResolved`/`HumanInputTimedOut` are appended, so `RunMemory.outcomes` is never populated for a node whose real agent outcome hasn't happened yet — the concern that originally motivated avoiding `HumanGate`'s events is satisfied by *which* of `HumanGate`'s events are reused (not `OutcomeReported`), not by avoiding the rendered pair altogether. A denial, or a prompt nobody answers before the timeout, is `StageError::SkillApprovalRejected`: the node does not start, and no `SkillBound` event is written for that node at all — partial trust is not partial binding.

## Rationale

- **Hash, not name or version, is the only thing that can't be forged by re-publishing.** Технически §4 of the competitive-waves spec already established this for identity; this ADR extends it to *trust*: the same property that makes a hash a good identity (content-derived, not author-asserted) makes it the only sound basis for "this is the content I already reviewed."
- **Reusing profile-trust's approval *mechanism*, not its *policy*.** ADR-0002 explicitly does not do hash-based drift detection for profiles — it trusts two static sources (bundled binary, local disk) outright. What this ADR borrows is narrower and already load-bearing: "an untrusted third-party declaration goes through the same elevation-approval round trip as anything else," which ADR-0002 states as the general shape. The specific policy here (pin-match vs. approval) is new to skills because, unlike a profile, a skill pack's provenance (`ProjectDir`/`UserDir`/`Registry`) doesn't imply the same level of first-party trust a bundled-or-local-disk profile does.
- **No second approval primitive — and "primitive" means the one with a renderer, not the one with the fitting name.** `EventPayload::ApprovalRequested`/`ApprovalDecided` and the `pending_approvals` view already existed, fully wired through persistence, but with **zero renderer**: no dispatcher, no CLI surface, nothing outside `surge-persistence` ever reads `pending_approvals`. Building a request/decide event pair for skills on top of that one would not have reused anything load-bearing — it would have been a second undelivered path next to a first undelivered path. `HumanGate`'s `HumanInputRequested`/`HumanInputResolved`/`HumanInputTimedOut` triple is the one primitive in this codebase that is actually delivered (`cockpit::dispatch::decide_action`, `surge inbox`), so it is the one this ADR reuses.
- **Binding at stage entry, not mid-stage.** A skill resolved partway through an agent's turn could differ from what the agent was told at prompt-construction time — the same reasoning that already governs `project.md` and `Binding` resolution. Gating happens before the session opens; `SkillBound` for a node is always emitted before that node's `SessionOpened`.

## Out-of-scope guarantees

This ADR explicitly does NOT promise:

- Persisting an approved hash back into the flow graph so a later run of the *same* graph skips re-approval. Every run re-checks the node's own declared pin against the freshly-resolved content; an unpinned declaration asks every run, by design (until a future task, if any, decides an approved run should write its hash back as a pin).
- Network-fetched `SkillProvider::Registry` resolution or a "configured registry root" surface — Решение §22 defers that; a node referencing `Registry` today resolves to `SkillError::NotFound` unless a caller has separately wired a real root.
- A rich operator UI for *choosing among* ambiguous candidates. The approval prompt lists every current candidate's hash, but the response schema is still the plain `approve`/`reject` `HumanGate` shares — the operator approves or rejects binding the lexicographically-smallest-hash candidate (a stable, deterministic tie-break), not a picker over N options. (Superseded in part by the second Correction below: `SkillError::Ambiguous` for an *unpinned* lookup is no longer a hard resolution failure — see there for what actually changed and why.)

## Consequences

- `AgentConfig::declared_skills()` reads `custom_fields["skills"]` rather than a dedicated struct field. `custom_fields` is `AgentConfig`'s existing, deliberately additive extension point; a new named field would have forced every `AgentConfig` struct literal across the workspace (production code and tests alike) to grow it in lockstep, for a capability most of those call sites don't exercise. This is revisitable once the shape stabilizes and existing call sites can absorb the field — see `crates/surge-core/src/agent_config.rs`.
- `surge_core::migrations::MAX_SUPPORTED_VERSION` moved 5 → 6 for `EventPayload::SkillBound`; a new enum variant is never "purely additive" from an old reader's point of view (see `docs/schema-versioning.md#event-payloads-run-log`), documented in `crates/surge-core/src/migrations/mod.rs` and `CHANGELOG.md`.
- `engine/stage/skill_binding.rs::bind_skills` owns the resolve/compare/approve/emit sequence and returns each bound skill's resolved instructions (`skill_binding::BoundSkill`); `engine/run_task.rs::execute_agent_node` is the one call site, wiring the same `gate_resolutions` registry `HumanGate` stages use (registering a decision sender only at the moment a prompt is actually requested, not eagerly at stage entry — an eager registration left a stale, unread entry in the registry for every node whose skills all bound without approval). `engine/stage/agent.rs::execute_agent_stage` appends each `BoundSkill::instructions` to the system prompt (after template rendering, so a pack's own `{{...}}`-shaped content is never mistaken for a template variable) before `SessionConfig` is built.
- Skill roots are constructed once and cached on the run's execution state (`RunExecutionState::skill_catalog`), not rebuilt per node: `<worktree>/.claude/{skills,plugins}` for `ProjectDir`, `~/.claude/{skills,plugins}` for `UserDir` — the Agent Plugins corpus (352 `SKILL.md`, all 47 `.claude-plugin/plugin.json` manifests) measured on a real machine lives entirely under `~/.claude/plugins`; `~/.claude/skills` is empty. `SkillCatalog::discover` (a synchronous filesystem walk-and-hash of every pack under all four roots) runs via `tokio::task::spawn_blocking`, never inline on the async worker.
- An unpinned or pin-fallback name/provider(/version) lookup that resolves `SkillError::Ambiguous` is not a resolution failure: every current candidate's content hash is listed in the approval prompt, and the lexicographically-smallest hash is the one `SkillBound` records if approved — a deterministic tie-break, not a guess, and not a UI for choosing among candidates (see Correction 2 and the revised Out-of-scope guarantee above).
- `ApprovalConfig::skill_approval` is read with node-then-profile precedence (`run_task::skill_approval_enabled`), matching `engine::stage::agent::effective_approvals`'s existing precedence for every other approval flag, rather than only the node's own `approvals_override`.
- `surge_core::validation::validate` calls `AgentConfig::declared_skills()` on every agent node (top-level and inside subgraphs) and reports a malformed declaration as `ValidationErrorKind::InvalidSkillsDeclaration` — a graph-load-time finding, before `PipelineMaterialized` and before a worktree exists, rather than a lazy failure the first time that node's stage is entered.

## Revisit conditions

- A `Registry` provider gains a real configured root and a distribution story — the resolution gap noted above becomes load-bearing rather than theoretical.
- Operators report that re-approving an unpinned skill on every run of an unchanged graph is friction rather than safety — at that point, writing an approved hash back as a pin (and where that pin should live) becomes its own decision.
- `custom_fields` stops being a reasonable home for `skills` (e.g. it grows enough sibling capabilities that `AgentConfig`'s call sites are worth updating in one pass) — promote it to a typed field then, not as a side effect of an unrelated task.
