# ADR 0017 — The Run Report is a projection of the event log, not a second source of run state

## Context

The competitive-waves plan promised a first-class Run Report: one document a reviewer opens to accept or reject a run without reading the transcript (`.autopilot/competitive-waves/manifest.md` R27/R28/R33; brief, verbatim: "`RunReport` type in `surge-core`, compiled from the event log: nodes, outcomes, verifier verdicts, evidence artifacts, cost, skills bound, memory receipts, steers, approvals"). Waves 1–2 of the same plan spent several tasks making sure the facts a report would need are actually *in* the log — `SkillBound` (Task 03), a typed `EscalationCause` (Task 17), context-pack receipts as a planned-but-not-yet-wired event (Task 06) — precisely so a later reader would not have to reconstruct any of it from configuration, prompts, or agent-reported text.

That earlier work only pays off if the report actually reads the log as its only input. Two other shapes were live options going in:

1. **Read from the engine's live `RunState`.** `surge_core::run_state::fold` already exists, is pure, and is unit-tested against event fixtures — reusing it looked at first like the obvious way to avoid a second fold over the same events.
2. **Read from `surge-persistence`'s materialized SQL views** (`cost_summary`, `stage_executions`, `artifacts`, `pending_approvals`) — already aggregated, already exposed on `RunReader`, and already the fastest path to "cost" and "evidence" sections.

Both were rejected, for reasons specific to what a report is *for* — recorded below so a future change to either `run_state` or the SQL views does not accidentally break the report's most important guarantee without anyone noticing.

## Decision

**`RunReport::compile(run_id, events: &[RunEvent]) -> RunReport` is a pure function of a plain event slice, and nothing else.** It takes no database connection, no `RunReader`, no live engine handle, and no `surge.toml`. `surge-cli`'s `surge run report` is the only place I/O happens: it resolves the run id, reads the full event log via `RunReader::read_events`, converts each `ReadEvent` to `surge_core::RunEvent` (a conversion `surge-cli::commands::run_fold::read_run_events` now shares with `fold_run_state`, so this is not a second reader of the raw log), and hands the plain slice to `compile`.

Two consequences follow directly, both load-bearing for the plan's own acceptance criteria:

- **An interrupted run is exactly as reportable as a finished one (R27.1).** `compile` never returns `Result` and never panics; a run whose log stops mid-flight (crashed daemon, still running) simply never sees a `RunCompleted`/`RunFailed`/`RunAborted` event, so `RunReport::completion` is `RunCompletion::Incomplete` — an honest answer derived from what the log actually contains, not an error and not a guess dressed up as one of `RunStatus`'s registry-table variants. **Parked is the one exception, and it is read, not excluded**: `RunParked{wake_at, runtime, basis, reason}`/`RunWokeFromPark` are ordinary log events (unlike `RunStatus::Crashed`, which `Storage::list_runs` assigns from a pid-liveness probe that no event ever records), so `RunCompletion` has its own `Parked` variant rather than folding a log-provable pause into the same bucket as a genuinely unexplained stall — see the "not `RunStatus`" note on `RunCompletion`'s own doc comment for the exact boundary this draws.
- **Waves 1 and 2 do not depend on wave 3 shipping.** Every emitter (`SkillBound`, `TaskVerified`, `TokensConsumed`, …) just appends its event; the report compiles from whatever is on disk whenever it is asked to, with no coupling to when or whether the report feature itself existed at record time. This is the same reasoning `.autopilot/competitive-waves/spec.md` §9 states directly: "это делает отчёт по оборванному рану бесплатным, а сам отчёт — не источником состояния, а его проекцией."

### Why not reuse `run_state::fold`

`run_state::fold`'s `RunMemory` (`artifacts`, `outcomes`, `costs`, the task ledger) looks, at a field level, like most of what a report needs. It is the wrong foundation anyway, because of what happens at the one transition a report cares about most: `apply`'s handling of `RunCompleted`/`RunFailed`/`RunAborted` replaces the entire `RunState::Pipeline { memory, .. }` with a bare `RunState::Terminal { kind, reason }` — no `memory` field at all (`crates/surge-core/src/run_state.rs`, the three `EventPayload::Run{Completed,Failed,Aborted}` arms of `apply`). That is correct for `run_state`'s actual job: once a run is terminal, the engine has no further use for its bookkeeping. It is exactly wrong for a report, whose single most important case — a **completed** run, which R33 says a reviewer must be able to accept or reject from the report alone — is precisely the case where reading `fold`'s final state would silently discard every outcome, artifact, and cost figure the run ever produced. `RunReport::compile` therefore keeps its own running tallies across the whole event slice instead of ever reading a folded terminal state.

### Why not read the SQL materialized views

`surge-persistence`'s `cost_summary`/`stage_executions`/`artifacts`/`pending_approvals` views are real, already exposed on `RunReader`, and already used elsewhere. Building the report on top of them would work for a healthy, fully-migrated run — but it would tie "can I get a report" to "did the view-maintenance triggers finish running for this log," a strictly narrower guarantee than "can this log be read at all," which is the one R27.1 actually asks for. It would also put `surge-core::run_report` behind `surge-persistence`'s SQLite dependency, inverting the workspace's layering (`surge-persistence` depends on `surge-core`, never the reverse) — `RunReport` would stop being a type any pure, DB-free context (a unit test, a future non-SQLite storage backend, `surge-orchestrator` itself) could construct from a `Vec<RunEvent>` fixture, which is the literal acceptance criterion this task shipped against: "Тест компиляции из вектора событий-фикстур, без БД."

### A verdict-correctness decision, not just a plumbing one

`compile` tracks the graph in force (from `PipelineMaterialized`/`GraphRevisionAccepted`) purely so it can reuse `run_state::node_has_verification_authority` — the same predicate `LedgerState::record_verified` already trusts — when folding a `TaskVerified` event into the `verdicts` section. A `TaskVerified` event with no authorized graph node behind it is surfaced as `VerdictResult::Unauthorized`, not silently accepted as `Verified` and not silently dropped: R33's "accept or reject from the report alone" is exactly the judgment a falsely-legitimate verdict would corrupt.

The same reasoning extends to `outcomes`: `OutcomeRejectedByHook` — the hook pipeline throwing out an agent-declared outcome after the fact — is folded into the matching `OutcomeEntry`'s `status: OutcomeStatus::RejectedByHook` rather than left in the tail branch. Reporting `outcomes` from `OutcomeReported` alone while separately flagging a forged `TaskVerified` would have told half the trust story and silently dropped the other half; a reviewer needs to see a hook-rejected outcome as rejected, not as an accepted one indistinguishable from a real success.

### The match in `compile` is exhaustive, not a `_ => {}` wildcard

`EventPayload` carries `#[non_exhaustive]`, but that attribute has no effect inside `surge-core`, the crate that defines it — a `match` here can be, and is, exhaustive over all variants. Every variant this report does not represent in any section is named explicitly in one grouped arm with a comment explaining why (bootstrap-internal telemetry, stage-internal wiring, loop bookkeeping, the dead `ApprovalRequested`/`ApprovalDecided` pair, etc.), rather than falling through an unlabeled `_`. The first version of this module used `_ => {}`, and a review pass found that 26 of the enum's 57 variants — including `RunParked`, `EscalationRequested`, and `OutcomeRejectedByHook` — silently vanished into it unnoticed. An exhaustive match turns "did we forget to handle the next new variant" into a compile error instead of a silent gap.

## Rationale

- **One fact, one home — but the home is chosen by lifetime, not by field-name overlap.** `run_state::RunMemory` and `RunReport` overlap heavily in *shape* (both have "cost," both have "artifacts by node") but need different *lifetimes* over the same events (memory to build the engine's next decision and expendable at terminal vs. a full-run summary that only matters once the run is over). Reusing a type whose lifetime is wrong for the new purpose is not reuse; it is a latent bug waiting for someone to call it on a completed run.
- **Purity is the feature, not an implementation detail.** Every other option (reading `fold`'s state, reading SQL views, reading a live engine handle) makes the report answer a slightly different question than "what does the log say" — and a slightly different question is exactly how a report stops being reconstructable from the log alone, the property Task 03's `SkillBound` event and this task both exist to prove.
- **No new dependency, no schema bump.** `RunReport::compile` reads variants that already exist (`SkillBound` since Task 03, `EscalationCause` since Task 17, the lifecycle/outcome/artifact/cost/approval events since M1–M6). Nothing about this task changes `EventPayload`'s shape, so `surge_core::migrations::MAX_SUPPORTED_VERSION` does not move.

## Out-of-scope guarantees

This ADR explicitly does NOT promise:

- **`memory_receipts` is populated.** `surge_core::context_pack::PackReceipt` exists and is computed at run start, but no `EventPayload` variant carries it into the log yet (that module's own doc names this as a separate, not-yet-done concern). `RunReport::memory_receipts: Vec<PackReceipt>` is the field §18 requires, wired to the log exactly like every other section — it is simply always empty until a future change emits the event. This is named here, in `surge_core::run_report`'s module doc, in `RunReport::caveats` — a real field `compile` populates, present in the JSON output too, not only in the Markdown/HTML prose — precisely so nobody, including a machine consumer parsing the JSON form alone, mistakes an empty list for "no memory was used."
- **A rich `approvals` correlation model.** Requests and their eventual decisions are listed as separate chronological entries, not paired — `HumanInputRequested`/`Resolved`/`TimedOut` carry an optional `call_id` that is `None` for `HumanGate`-driven pauses, so pairing every approval family's request to its decision would require guessing correlation the log does not make explicit everywhere. A still-pending request with no following decision entry is itself the fact R27.1 cares about, not a defect in the rendering.
- **Coverage of `EventPayload::ApprovalRequested`/`ApprovalDecided`.** Per [ADR 0015](0015-skill-binding-trust-via-content-hash.md), that pair has no production emitter and no renderer anywhere in the codebase today. Including it in `approvals` would list an approval flow that never actually asked anyone anything; `compile` ignores it by construction (see the module's own test asserting this).
- **A structure-delta section.** Explicitly deferred by the plan itself as a stretch goal beyond wave 3 (manifest R32).

## Consequences

- `crates/surge-core/src/run_report/mod.rs` owns the nine section types (`NodeSummary`, `OutcomeEntry`, `VerifierVerdict`, `EvidenceEntry`, `CostTotals`, `SkillUsage`, `PackReceipt` reused as-is from `context_pack`, `SteerEntry`, `ApprovalEntry`), the supplementary `RunHeader`/`EscalationEntry`/`caveats`, and `RunReport::compile`; `crates/surge-core/src/run_report/render.rs` owns `render_json`/`render_markdown`/`render_html`, kept in a separate file so the compiler and the presentation logic can change independently (the compiler's contract — "pure projection of events" — has nothing to do with how a table gets drawn in HTML).
- `crates/surge-cli/src/commands/run_fold.rs` gained `read_run_events(reader, run_id) -> Vec<RunEvent>`, factored out of the existing `fold_run_state` so `surge run report` and `surge inbox`/`surge resolve` share the one `ReadEvent → RunEvent` conversion instead of each command deriving it independently.
- `surge run report <run_id> --format json|md|html` (default `md`, via `#[arg(default_value = "md")]` alone — `RunReportFormat` does **not** also derive `Default`, which would be a second, dead source of the same default) is the new CLI surface (`crates/surge-cli/src/commands/run.rs`). Output is written with a single `writeln!` whose error is discarded rather than `println!` (which panics on `BrokenPipe`, e.g. `surge run report X --format html | head`) — the same swallow-per-write `inbox.rs::print_inbox_to` already uses for the same reason.
- **Every value the HTML renderer interpolates is escaped, uniformly** — including values "safe by construction" today (a validated `NodeKey`, a hex `ContentHash`, a `{:?}`-formatted enum) — rather than escaping only the free-form `String` fields judged risky. A review pass found the original code escaped some but not all interpolation sites, and no test exercised most of them; the fix and its regression test (`every_string_carrying_section_escapes_its_xss_fixture`) seed the same XSS payload into every `String`-carrying field this renderer touches and assert per-section, not just once, that the raw tag never survives. A `render_html` unit test and a CLI integration test additionally assert the output contains no `<link>`, `<script src>`, or `http(s)://` reference of any kind (R29).
- `VerdictResult::Unauthorized` is new vocabulary with no upstream equivalent — `run_state::LedgerState` simply drops an unauthorized `TaskVerified` on the floor (increments `rejected_verifications` and moves on); the report chooses to surface it instead, because a reviewer deciding "accept or reject" needs to see the attempted forgery, not a `verdicts` list that quietly has one fewer entry than the log does. `OutcomeStatus::RejectedByHook` is the same move applied to `outcomes`.
- `CostTotals.uncosted_token_events` counts `TokensConsumed` events with `cost_usd: None`; every renderer states the cost figure as a floor ("at least $X (+N events without a recorded price)") whenever this is nonzero, rather than silently treating an unpriced event as free.
- `RunReport::caveats` is a real field on the type, populated by `compile` itself (not only prose in a renderer), specifically so the JSON form carries the same "`memory_receipts` is always empty, and here is why" warning the Markdown/HTML forms show — an empty `memory_receipts: []` with no accompanying caveat would read to a machine consumer as "memory was not used," the exact false reading this field exists to prevent.

## Revisit conditions

- A future task wires `PackReceipt` into the event log (Task 06's named follow-up) — `RunReport::memory_receipts` starts populating with no signature change; the "always empty" test and doc note in `run_report`'s module doc should be updated in the same change.
- `run_state::RunMemory` is ever changed to survive past the terminal transition (e.g. if a future feature needs post-terminal bookkeeping for its own reasons) — at that point, whether `RunReport::compile` should delegate part of its work to `fold` becomes a live question again; until then, the two folds are deliberately independent.
- The `approvals` section's flat chronological shape stops being legible for a run with many approval round trips — pairing requests to decisions (keyed by node + a synthesized ordinal, since not every family carries a stable correlation id) becomes its own decision at that point, not a silent addition to this one.
