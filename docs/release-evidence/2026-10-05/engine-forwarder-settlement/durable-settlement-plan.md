# Durable host settlement: proposed exact-run boundary

Status: PROPOSED. Authored by security scout at root request; requires root owning decision and a DIFFERENT independent reviewer. This document is not an acceptance verdict. Existing engine repair count remains unchanged. No Rust/schema implementation or build was performed.

## Problem and source evidence

- `surge-daemon/src/intake_completion.rs:201` reconstructs terminal outcomes from persisted events; `automation_merge_gate.rs:204` consumes that result at startup/periodically. Journal terminality does not prove actual SQL/forwarder settlement.
- `surge-cli/src/commands/engine.rs:347` reads completed history independently of the live result; bootstrap recovery has a separate event-history loop around `bootstrap.rs:344`.
- `runs/storage.rs:384` acquires the in-process writer token then actual `events.sqlite.lock`, before run migration/reader/actor startup. `writer_slot.rs:15` retains both through WriterLease. Neither lock availability nor process death is a successful completion receipt.
- `runs/reader.rs:344` finite feed and actual SQL read lease retain the same WriterLease. This is the correct exclusion to extend through publication.
- `work_items/recipe_capacity.rs:9` and migration `0026_recipe_admissions.sql` demonstrate durable pre-effect opening epochs/latest-exact receipt comparison, but are provider recipe admissions, not run writer or host settlement authority.
- `runs/registry_exec.rs` supplies cancellation-fenced IMMEDIATE writes. Its volatile commit fence prevents late caller-abandoned commits but does not itself establish crash recovery authority.
- `work_items/owned_flow/refusal_delivery.rs:46` acquires the actual normal writer guards outside `Storage::open_run_writer`; it must participate too.

## Concrete scope and non-goals

Durable proof covers the exact host execution's journal writer, execution-owned event readers, finite internal forwarder and actual SQL workers. It does not claim every independent public subscriber, unrelated Storage clone, provider process, MCP child or machine resource has stopped. Existing provider/MCP verification and protected failed-close policy remain separate prerequisites and unchanged.

Persisted RunCompleted/RunFailed/RunAborted remain history. Durable confirmation is an additional host receipt. A failed or cancelled completion may have valid terminal history but no host confirmation. UNKNOWN is a first-class result, never implicit success.

## Additive registry records

Add one registry migration, with no successful backfill. Use typed per-run OpeningId (fresh opaque random ID) plus monotonic registry epoch and bounded versioned payloads. Two conceptual tables:

1. `run_host_openings`: epoch primary key, unique opening ID, run ID, owner mode (JournalOnly or Engine), captured journal/lock namespace identity, status (Opening, JoinedWriter, ConfirmedExecution, Interrupted/Failed), and nullable typed failure diagnostics. Latest means greatest epoch FOR THAT RUN, not provider runtime/recipe.
2. `run_host_settlements`: unique opening ID foreign key, run ID, exact journal identity, sealed sequence, canonical journal-prefix digest, terminal-event sequence/kind/digest where applicable, evidence provenance (JoinedExecution or ExplicitHistoryRevalidation), scope version, and bounded receipt payload. Store exact opening references redundantly only with transaction validation.

Owner mode and state are not arbitrary caller-writable strings. Persistence exposes opaque opening/settlement capabilities and typed enums; no public method accepts an arbitrary receipt, opening ID or raw status to bless a run. Registry rows alone cannot grant OS writer authority.

Journal identity binds actual held objects, not merely run ID/pathname. Define `JournalIdentityV1` as platform tag plus identities of runtime-home directory, run directory, original journal lock and database. Windows fields are SDK FILE_ID_INFO.VolumeSerialNumber (u64) and FileId.Identifier ([u8;16]) from the existing namespace `Identity` implementation in `state_home/windows/namespace.rs:44`; use retained handles and a narrow crate-private identity observation method, preserving existing namespace verification. `state_home/test_security.rs:226` independently demonstrates the exact SDK query for tests. Unix fields are fstat metadata.dev()/ino() u64 from retained directory/lock/database descriptors; use existing O_NOFOLLOW/O_CLOEXEC/openat and fstatat comparison pattern in `work_items/start_preparation/secure_lock.rs:171-195,299-340`. Reject symlink/reparse, wrong type, delete-pending where supported and multiply linked regular journal/lock files. Keep descriptors live through verification/publication/authorization; compare held identity to current linked entry using existing platform namespace verification or Unix fstatat(AT_SYMLINK_NOFOLLOW). This is an internal read-only identity observation, not new general filesystem mutation authority.

`JournalPrefixDigestV1` is SHA-256 over exact byte framing: ASCII `surge.host-settlement.journal-prefix.v1` followed by one zero byte; run ID canonical display UTF-8 (exact `RunId::to_string()` spelling, require parse/render round-trip equality), length u32 little endian and bytes; one numeric platform tag byte (1 Unix, 2 Windows); identities in FIXED order home, run directory, journal lock, journal DB. Each Unix identity is dev:u64LE then ino:u64LE; each Windows identity is VolumeSerialNumber:u64LE then FileId.Identifier's exact16 SDK bytes. Then sealed prefix:u64LE; each ordered row is sequence:u64LE, timestamp:i64 two's-complement LE, STORED schema_version:u32LE, kind UTF-8 byte length:u32LE and bytes, raw stored payload length:u64LE and bytes. No separators, JSON reserialization or native integer representation. Stored schema version is semantically necessary: `reader.rs:78,93,124,147` selects it separately and passes it to migration.

Hash/validate inside ONE actual SQLite read transaction/snapshot while original exclusion is held: before/after streamed row iteration, `COALESCE(MAX(seq),0)==sealed_prefix` and `COUNT(*)==sealed_prefix`; both queries are in the SAME transaction as rows. Require all sequences exactly1..prefix with checked counters and positive i64 domain, no gap/duplicate and NO suffix above prefix. Zero means table empty, not merely no rows matching `<=0`. Read bounded batches within that same retained transaction, streaming hash over entire prefix and applying current journal decoding/size validation; overflow/invalid kind UTF-8 refuses. Terminal receipt additionally stores terminal sequence, kind, STORED schema version, and SHA-256 of the terminal row's SAME framed bytes; folded decoded history must contain the single valid matching terminal outcome. Unknown receipt/digest/platform tag version refuses. Fixed independent vectors include same raw row with versions1/2 producing distinct bytes/digests, invalid signed/overflow/missing migration versions, raw-kind/decoded mismatch, extra suffix including nominal zero-prefix, and fixed Unix/Windows identity ordering. Do not generate expected vectors with production encoder.

## Normal engine receipt and exact release order

Engine declares Engine ownership before executing any engine work or creating feed obligations. It obtains a private settlement publisher retaining the SAME original WriterLease and opening capability. This publisher is not a substitute/new OS lock and cannot append journal events.

Normal sequence:

1. Engine completes outcome/event logic and existing external writer cleanup prerequisites.
2. Serialized seal closes command receiver, rejects later commands, captures prefix and closes actual writer connection; await actor join and check receipt plus join independently.
3. Await internal forwarder and every real SQL worker, offering exactly the sealed prefix. Drop all execution-owned reader/estimator/feed objects and verify returned prefix agreement. Keep the publisher's original lease alive, so a replacement writer remains Busy.
4. A final bounded independently owned journal verification job, still under that lease, reads exact namespace identity and canonical prefix digest/terminal history. Join it and drop its connection/reader before publishing. No transient select may abandon this job. The proof concerns the final joined prefix, not an earlier watermark.
5. In one IMMEDIATE registry transaction, compare exact latest run opening/mode/identity and write ConfirmedExecution plus immutable JoinedExecution receipt. The actual registry publication worker retains the same lease until the commit or rollback truly finishes, even if its async caller is cancelled. After it exits, drop publisher and its lease.
6. Only after publication success AND actual publication-worker join/resource release return normal outcome. Publication error becomes SettlementFailed, preserves original outcome and no confirmed success. If a commit succeeded but caller was then hard-aborted, durable receipt may remain valid only because ALL execution/SQL prerequisites already completed before the commit; caller interruption still does not itself prove success.

Do not wait for Arc uniqueness inside actor close. The publisher intentionally retains exclusion after actor/feed exit. Resource release before receipt validation would permit a newer writer to race and falsely associate its journal with the older owner.

Public RunWriter::close stays a writer-close guarantee, never Engine completion. JournalOnly close may record JoinedWriter for its own opening after actor join and dropping its own reader, while holding publisher lease. It does not emit ConfirmedExecution and cannot erase an earlier unresolved Engine obligation merely by appending informational recovery or cleanly closing. Prior Engine provenance/obligation must be carried forward explicitly in opening records, not lost when latest mode is JournalOnly.

Exact unresolved-obligation transition rules: add nullable `unresolved_engine_opening` and nullable `last_confirmed_engine_receipt` to each opening payload, copied transactionally from the previous latest row. A JournalOnly opening inherits both unchanged; JoinedWriter close changes neither and cannot produce execution authorization. Beginning Engine execution sets unresolved_engine_opening to its own opening ID, preserving prior unresolved origin in audit predecessor link. Engine-mode declaration is a durable CAS before feed/work, not an in-memory flag. JoinedExecution publication is permitted only if latest opening equals that Engine owner, unresolved_engine_opening equals its own ID, original lease is held, and all final proof matches; it atomically clears unresolved and sets last_confirmed_engine_receipt to its new receipt ID. Failure/interruption leaves unresolved unchanged. ExplicitHistoryRevalidation uses its own Revalidation owner mode, preserves prior unresolved origin for audit and may clear it ONLY upon fresh revalidation publication under that owner's lease, with distinct provenance. A later JournalOnly close does NOT rebind an old execution receipt to its new epoch, even if journal bytes happen to be unchanged; consumers return Unknown until normal authorized Engine completion or existing explicit history revalidation. Thus it cannot conceal interrupted Engine ownership. Fresh valid latest JoinedExecution receipts still authorize automatic startup/periodic recovery under existing policy; no new operator action is required for those.

## Crash windows and interruption

- Before opening barrier: no journal effects, older proof remains valid if exact identity/prefix still matches.
- After barrier/before actor startup: latest unconfirmed Opening; older proof invalid.
- During append/SQL or after RunCompleted but before actor/feed joins: UNKNOWN; process death releases OS handles without manufacturing receipt.
