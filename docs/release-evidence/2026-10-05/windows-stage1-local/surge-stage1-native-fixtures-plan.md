## Elevated launch isolation

The current script's `$root` grants the standard probe account FullControl and
contains `surge-persistence-probe.exe`. NEVER execute that copy elevated, and do
not use its working directory, dependency files, receipt paths, helper scripts or
environment as trusted elevated-launch input.

Create a separate provisioner-owned launch tree beneath a validated trusted local
NTFS ancestor. Its initial protected DACL grants mutation only to the provisioner
and trusted Administrators/System, with no standard-probe or foreign-account
mutation rights. Independently validate actual owner/DACL and every ancestor:
neither test account may replace a component through parent delete-child access,
reparse routing, inherited grants or a writable ancestor. Retain traversal handles
without delete sharing and retain immutable read access to the candidate executable
and private dependency files through child creation/exit. ACLs alone on the final
executable do not establish a protected launch chain.

Copy the candidate directly from the provisioner-controlled build output, before
any standard-user access, into this launch tree. Record source candidate revision,
original build-artifact identity and cryptographic hash; hash the actual protected
copy and require equality. Never copy it back from `$root`, trust a hash supplied
by a standard-user receipt, or launch a pathname whose identity can subsequently
be replaced by a test account.

Use an absolute executable path, a protected working directory, and protected
stdout/stderr/structured-receipt destinations created by the provisioner. Bundle
any non-system runtime dependencies in the same protected tree and inventory/hash
them. Constrain DLL/search and environment inputs to that tree and trusted system
directories: no writable `$root`, checkout, user-profile search directory, PATH
entry or standard-user config/script loading in the elevated helper. The helper
does not load plugins or spawn shell commands. Validate this for the actual
candidate dependency closure before launch; missing dependency resolution is a
failed setup, not a fallback to a user-writable directory.

The elevated invocation has one literal reviewed test filter plus literal
`--ignored --exact --nocapture --test-threads=1`. Additional arguments/environment
are generated by the provisioner from its own freshly recorded SIDs, isolated
protected paths and per-invocation nonce. They are passed as data through the
native process-creation boundary with explicit Windows argument encoding, never
through shell interpolation. No filter, executable, path, command fragment or
privilege selection comes from a standard-user test/receipt. Elevated fixture
data lives in the protected tree; the standard-user fixture uses a separate
subtree and cannot redirect the elevated helper's work by editing data there.

The parent validates the elevated exit status and a protected receipt bound to
the expected candidate hash, exact filter, actor SID and invocation nonce. Receipt
contents are data only. Only after the child has exited may the parent copy a
sanitized receipt to the ordinary reporting location. A standard-user-authored
receipt never stands in for the elevated observation.

## Token ownership and privileges

Use `DuplicateTokenEx` to create a separately owned primary token from the
provisioner's queried token. Request only rights needed to query/adjust its
default owner and required privileges and to launch its owning helper. Any
TokenOwner change uses `SetTokenInformation(TokenOwner)` on this duplicate only;
require a legitimate owner SID present with the required owner eligibility,
re-query actual TokenOwner and verify it differs from actual TokenUser. Fail
setup if that configuration cannot be established. Never adjust the long-lived
provisioner process token or the standard-user token.

Any needed privilege enablement, including SeRestorePrivilege for assigning the
foreign fixture owner, is confined to a separate duplicated primary token for the
specific protected helper performing that setup. Check privilege-adjustment
results including not-all-assigned and re-query effective enabled state. Enable
only the named required privilege, not every available privilege. Production
standard-user tests receive no such privilege. Do not use persistent thread
impersonation or globally enable privileges to make process creation succeed.
Required launcher rights must already be available to the provisioner; otherwise
report setup failure. Every duplicate token belongs to the resource ledger and
is closed on every path after its launch/usage completes.

## Resource ownership and failure settlement

Use one provisioner-owned ledger initialized before the first mutation. Record
each resource immediately after acquisition: standard account name/SID and
created-by-this-run flag; foreign account name/SID and created flag; profiles
actually created by this run and their SIDs; standard and elevated child process
handles/IDs with launch and observed-exit state; each duplicate token/handle;
protected launch/data/receipt trees; ordinary fixture tree; original environment
values. Never infer ownership from a matching prefix or account name alone.

All success, failed launch, nonzero exit, timeout, observer failure and exception
paths enter the same finalizer. First release any owned test observation barrier,
then settle EVERY launched child type: retain its original process handle, request
termination if necessary and wait for actual observed exit. A successful kill
request or expired wait is not exit evidence. Handle each child independently so
one kill/wait exception cannot bypass settlement of another. Do not lose a live
child handle merely because its stdout/receipt read failed.

After exit is confirmed for all owned children, attempt each independent cleanup
step even if another fails: close token/process/file handles; restore original
environment; remove only profiles recorded as newly created for the two exact
owned SIDs; remove only the two accounts whose creation succeeded in this run;
remove only the owned isolated trees. A failed profile cleanup is recorded and
does not suppress the independent other-account/profile cleanup attempt. Keep
dependency ordering for a single resource when a later action would invalidate
the ability to safely finish an earlier one. Never delete preexisting profiles
or accounts. Dispose handles exactly once and record any cleanup error.

If ANY child remains unobserved or unsettled, preserve both accounts, their
profiles and both protected/ordinary fixture trees; do not make a partial deletion
claim. Continue safe independent actions such as restoring the provisioner's
environment and closing no-longer-needed duplicate token handles, but retain
the unsettled process owner and evidence for explicit diagnosis. Report all
affected resource identities and the settlement failure; do not run recursive
path cleanup while the child might still be using it. No retry-to-green outcome.

Aggregate the original test/setup failure and all settlement/cleanup failures in
the final failed receipt. Avoid a throwing `finally` body whose first cleanup
failure hides the original error or skips the remaining resources. A green probe
requires the intended observations AND completed required settlement/cleanup.

## 1. Administrative default owner: protected creation below trusted ancestor

Purpose: prove explicit creation owner uses effective TokenUser when that same
effective token has Administrators as its different default TokenOwner. Creation
under an administrator-owned ancestor alone does not establish this condition.

1. Elevated provisioner queries both TokenUser and TokenOwner using independent
   SDK calls. Require the effective creation token's actual TokenOwner to equal
   Builtin Administrators. Elevation or Administrators membership alone does not
   prove this. If the usual provisioner token lacks that default owner, use a
   separately owned duplicated primary token and verified legitimate TokenOwner
   setting under the token contract above, then re-query it; otherwise fail setup
   with a precise reason.
2. Under that token, create an isolated ancestor without explicitly setting its
   security-descriptor owner. Supply an initial protected DACL granting only the
   target standard user's required traversal/creation rights and trusted
   administrator/system fixture rights. Inspect actual resulting owner, DACL and
   volume through SDK; require actual owner Builtin Administrators.
3. Launch the protected-copy helper under the verified duplicate primary token,
   following the exact elevated launch contract above. The helper independently
   re-queries its EFFECTIVE
   creation token, requires TokenOwner=Administrators and TokenUser!=TokenOwner,
   then invokes actual production home/permanent-database creation below a
   dedicated safe ancestor. Record those two SIDs. SDK observer requires the new
   protected objects' actual owner to equal this helper's TokenUser, never its
   Administrators TokenOwner, with exact user-only DACLs. It settles Storage and
   exits; parent checks its exact exit and receipt. The elevated helper runs only
   this creation oracle, not daemon/runtime acceptance. Provisioner credentials
   and SID arguments are setup data, not substitutes for token verification.
4. In a second isolated subtree, record the complete ancestor owner/DACL and a
   sentinel. As the standard user,
   invoke actual production RuntimeHomeOwner/Storage creation for a missing home
   below it. Do not precreate the target home or database in the fixture helper.
5. Independently inspect home and permanent database. Require actual TokenUser
   owner, exact protected current-user-only DACL and the expected inheritance
   flags for each object. Verify normal storage use/settled closure succeeds.
6. Require ancestor owner/DACL/sentinel unchanged, then release and clean fixture.

Keep the two receipts precise: step 3 is the actual differing-default-owner
oracle; steps 4-6 prove standard-user creation beneath a trusted administrative
ancestor. Both must execute. If only steps 4-6 can run, the default-owner gap
remains open. Do not assert the standard user's default TokenOwner was
Administrators. The SDK observer must accept the explicit expected actor SID for
the elevated subcase without weakening the fixed standard-user SID assertion in
all existing normal probes.

## 2. Foreign owner: isolate owner refusal from DACL refusal

Purpose: an existing home owned by a different local SID must be rejected even
when its otherwise acceptable DACL grants the executing user access.

1. Use a second isolated local account/SID as the foreign owner. Record that it is
   neither the standard test user's SID nor a trusted Administrators/System SID.
   Provisioning uses the protected setup helper with the separately duplicated
   primary token and verified required owner-assignment privilege described
   above; it does not grant that privilege to the standard-user test process.
2. Create the candidate home and a sentinel; install the actual foreign owner
   and the exact protected current-test-user-only DACL otherwise expected for a
   home, including expected inheritance bits. Verify those facts with SDK before
   launching production. This isolates the owner predicate rather than relying
   on an unrelated bad DACL or access-denied failure.
3. Standard user captures full owner/DACL representation, sentinel bytes, root
   entry inventory and absence of registry SQL/runtime children. Attempt the real
   production home/storage open and require typed security refusal before SQL or
   directory initialization, not Busy and not a successful fallback.
4. Independently compare all captured state afterward. Owner, DACL, bytes and
   entries must be unchanged. No ACL repair, replacement home or empty SQL file.

If a necessary fixture privilege or foreign SID cannot be established, fail the
dedicated setup explicitly. Do not skip the assertion or substitute a widened ACL
test already covered elsewhere.

## 3. Initial creation security: observe the actual production creation boundary

Purpose: test the security descriptor installed by the actual native FILE_CREATE
operation before any caller can validate, write, repair or make further objects.
An after-open check alone cannot distinguish initial protection from late repair.

Add one narrow `#[cfg(all(test, windows))]` observation hook to the common native
creation boundary. It runs only after the synchronous NtCreateFile returns actual
success for FILE_CREATE and a valid owned descriptor has been formed, but before
the caller's first security validation, data write, flush or subsequent creation.
It does not run for FILE_OPEN/collision reopens, does not mutate the descriptor,
and is absent in production builds. Match a per-test token and an exact expected
object/phase; use scoped/thread-local registration so concurrent tests cannot
intercept unrelated operations. No hook may manufacture creation success.

1. Preconfigure a safe fixture parent with an inheritable outsider read grant
   which must not survive onto the protected runtime child. Outsider mutation is
   still forbidden; the ancestor must pass the genuine production ancestor
   contract. Establish this parent with independent SDK calls.
2. Run real missing-home creation, paused by the hook on its successful native
   creation. A separate observer thread/process opens the actual created object
   with compatible sharing and READ_CONTROL/read-attributes access. It queries
   actual owner/control/DACL/ACEs through the independent SDK observer; do not
   call production security validation as the assertion.
3. Require actual standard TokenUser owner, protected DACL, exact user-only ACE
   mask and expected inheritance flags, and absence of the outsider ACE. Observer
   acknowledges the exact identity/phase before the production thread resumes.
4. Repeat at the actual permanent database FILE_CREATE boundary through Storage.
   Require correct file policy independently, no outsider grants, and zero file
   length at this pre-write observation. Both home and database observations are
   mandatory; a missing hook acknowledgement fails the test.
5. Resume normal production, require successful storage use and full writer/pool
   settlement, then independently compare final object identities to those
   observed at creation. The hook cannot replace or recreate the original object.

Use bounded channels/child timeouts and unconditional failure-path release of the
test barrier; a failed observer must not strand the producer. Keep test hooks out
of public exports and normal production logging. The observer is read-only and
holds no handle past the explicitly acknowledged observation phase unless the
oracle requires it. Path polling after completion is not an equivalent test.

This establishes initial-descriptor evidence at the production syscall boundary;
it does not claim filesystem power-loss durability or arbitrary scheduler-wide
temporal coverage. Process crash probes and VM hard-stop evidence remain distinct.
